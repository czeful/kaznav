# Архитектура робота простым языком

Этот документ — дополнение к `docs/kak_rabotaet_kod.md`. Там описано, **где в коде** что лежит. Здесь — **как
думает робот**: какие модели в нём работают, зачем каждая, сколько раз она вызывается и что именно получает и
отдаёт. В середине документа робот проходит один эпизод от начала до конца на настоящем примере.

Правило документа: каждый термин объясняется там, где появляется впервые. В конце есть словарь всех терминов.

Все цифры времени и количества взяты из настоящих прогонов на dev-эпизодах (это тренировочные квартиры, не тест).

---

## 1. Робот как человек, который ищет вещь в чужой квартире

Представь, что тебя привели в незнакомую квартиру и сказали по-казахски: «Төсекті тауып берші» («найди кровать»).
Что ты делаешь?

1. **Понимаешь просьбу**: «нужна кровать; она обычно в спальне, большая, с подушками».
2. **Осматриваешься**: поворачиваешься на месте, запоминаешь, где стены, где проходы.
3. **Решаешь, куда идти**: «вон та дверь похожа на спальню — пойду туда».
4. **Высматриваешь кровать**: на каждом шаге смотришь, нет ли её.
5. **Увидел что-то похожее** — подходишь ближе.
6. **Приглядываешься**: «это точно кровать или диван?» — и только тогда говоришь «нашёл».

Наш робот делает то же самое. Каждый шаг выполняет своя модель или свой алгоритм:

| что делает человек | что делает робот | кто это делает |
|---|---|---|
| понимает просьбу | превращает команду в список английских описаний цели | **VLM** (Qolda или Qwen) — разбор команды |
| запоминает стены и проходы | строит **карту занятости** по камере глубины | алгоритм (без нейросети) |
| чувствует «туда идти перспективнее» | строит **карту ценности** | **SigLIP 2** |
| высматривает цель | ищет описания цели на каждом кадре | **детектор MM-GroundingDINO** |
| понимает, где кончается предмет | вырезает точный контур найденного | **SAM 2** |
| помнит «кажется, кровать была там» | хранит **кандидатов** с уверенностью | алгоритм памяти |
| выбирает путь и идёт | планирует путь и ведёт колёса | планировщик Дейкстры + контроллер |
| приглядывается перед ответом | спрашивает «это кровать?» и решает, остановиться ли | **VLM** — проверка + **калибровка** |

**Термины из таблицы:**
- **VLM** (Vision-Language Model, визуально-языковая модель) — нейросеть, которая понимает и картинки, и текст:
  ей можно дать фото и задать вопрос словами. У нас две такие модели: **Qolda** (казахская, создана ISSAI) и
  **Qwen3-VL** (мультиязычная, Alibaba). Обе размером около 4 миллиардов параметров.
- **Параметр** модели — одно число внутри нейросети, выученное при обучении. «4 миллиарда параметров» — мера
  размера и «ума» модели.
- **Детектор** — модель, которая находит на картинке объекты и обводит их **рамкой** (прямоугольником) с числом
  уверенности от 0 до 1.
- **Алгоритм** здесь — обычная программа с формулами, без обучения: карта, планировщик, контроллер.

## 2. Все модели системы: кто, зачем, сколько раз

### 2.1. Сводная таблица

| модель | что это | вход → выход | сколько раз | время одного вызова | где работает |
|---|---|---|---|---|---|
| **Qolda-4B** или **Qwen3-VL-4B** (одна из двух, в зависимости от варианта) | VLM | **разбор:** текст команды → JSON с целью и 3 английскими гипотезами | **1 раз на команду** (дальше берётся из кэша) | ~6–7 с (Qolda), ~5.5 с (Qwen) | отдельный сервер на видеокарте, ~8 ГБ |
| | | **проверка:** кусок кадра (кроп) + вопрос «это кровать?» → вероятность «да» | **~2–3 раза за эпизод** (только когда робот рядом с кандидатом) | ~0.9 с (Qolda), ~1.3 с (Qwen) | тот же сервер |
| **MM-GroundingDINO base** | открытый детектор | кадр + одна текстовая гипотеза → рамки с уверенностью | **каждый шаг × число гипотез** (3 прохода за шаг; ~400–700 шагов → ~1200–2000 проходов за эпизод) | ~0.1 с на проход (оценка) | процесс робота, видеокарта |
| **SAM 2.1 tiny** | сегментатор | кадр + рамка → маска (точный контур объекта) | только в шагах, где детектор что-то нашёл (~30% шагов): 1 кодирование кадра + 1 маска на рамку | доли секунды | процесс робота, видеокарта |
| **SigLIP 2 base** | модель «картинка ↔ текст» | кадр + тексты гипотез → насколько кадр похож на каждую | **каждый шаг**: 1 кодирование кадра; тексты кодируются 1 раз за эпизод | доли секунды | процесс робота, видеокарта |
| NLLB-200 600M | переводчик | казахский текст → английский | 1 раз на команду, **только в вариантах «переводчик»** | ~1 с | процессор |
| RT-DETR R101 | закрытый детектор (80 классов COCO) | кадр → рамки известных классов | каждый шаг, **только в строке «как VLFM»** | — | видеокарта |
| «Идеальный детектор» | не модель: берёт правду из разметки сцены | — | каждый шаг, **только в строке «потолок»** | мгновенно | — |

**Итого за типичный эпизод метода**: ~3–4 вызова VLM (1 разбор + 2–3 проверки), ~1500 проходов детектора, ~500
кодирований SigLIP, ~150 кодирований SAM. Время эпизода — 3.5–6 минут; из них на VLM всего ~10 секунд.
Остальное — детектор, SAM, SigLIP, карта и сама симуляция: ~0.5 с на шаг при трёх гипотезах против ~0.24 с у
базовой линии с одной.

**Термины:**
- **Гипотеза** — одно английское описание того, как может выглядеть цель: «bed with white sheets», «bed in a
  bedroom». VLM пишет несколько гипотез, потому что не знает, как именно выглядит кровать в этой квартире.
- **Кроп** — вырезанный кусок кадра вокруг рамки кандидата (с небольшим запасом по краям).
- **Кэш** — сохранённый результат, чтобы не считать его заново. Разбор одной и той же команды при температуре 0
  всегда одинаков, поэтому его можно сохранить.
- **Сервер модели** — отдельная программа, которая держит модель в видеопамяти и отвечает на запросы по сети
  (здесь — внутри одного компьютера, `localhost`).
- **Открытый детектор** (open-vocabulary) — ищет любые объекты по текстовому описанию. **Закрытый** знает только
  фиксированный список классов (например, 80 классов COCO) и не понимает фраз вроде «carved wooden chest».
- **Сегментатор** — модель, которая для каждого пикселя решает, принадлежит ли он объекту. Результат — **маска**:
  чёрно-белая картинка, где белое — объект.
- **Шаг** (шаг решения) — один цикл «посмотрел → подумал → поехал». У колёсного робота шаг длится 0.5 секунды
  симулированного времени.

### 2.2. Почему моделей так много и почему не одна большая VLM

- **VLM медленная.** Один её вызов — около 1 секунды и дольше, а шагов в эпизоде сотни. Если звать VLM на каждом
  шаге, эпизод шёл бы час. Поэтому VLM работает редко: один раз, чтобы понять команду, и в конце, чтобы проверить
  находку.
- **Детектор быстрый и даёт число уверенности.** Он работает на каждом шаге и выдаёт точные рамки с уверенностью,
  а это нужно для карты кандидатов и порогов.
- **SigLIP даёт чувство «где теплее»**, даже когда цель ещё не видна: кадр со спальней ближе к «bed», чем кадр с
  кухней.
- **SAM нужен, потому что рамка неточна**: в рамку попадает стена за кроватью, и без маски робот «поставил» бы
  кровать на стену.
- **Научная причина:** детектор, SAM и SigLIP **одинаковы во всех вариантах**. Отличается только VLM, поэтому
  разница в результатах между Qolda и Qwen — это разница в понимании языка.

### 2.3. Где что запущено (процессы и память)

```
Windows 11
└── WSL2 (Linux внутри Windows)
    ├── процесс робота: tools/run_eval.py (окружение habitat_env)           ~3.5 ГБ видеопамяти
    │     Habitat-Sim (рендер квартиры) + MM-GroundingDINO + SAM 2 + SigLIP 2
    │     карта, планировщик, контроллер, логи
    │                │  HTTP-запросы на 127.0.0.1 (как веб-сайт, но внутри компьютера)
    │                ▼
    └── сервер VLM: servers/qolda_server.py :23333  или  servers/qwen_vl_server.py :23334   ~8 ГБ
```

На видеокарте 12 ГБ: сервер VLM (~8 ГБ) + процесс робота (~3.5 ГБ) ≈ 11.7 ГБ. Поэтому **одновременно работает
только одна VLM**, и `run_matrix` сам по очереди поднимает и гасит нужный сервер.

**Термины:**
- **WSL** (Windows Subsystem for Linux) — Linux, работающий внутри Windows. Habitat-Sim работает только под Linux.
- **HTTP** — способ обмена сообщениями между программами (как браузер с сайтом). Процесс робота отправляет серверу
  VLM запрос «вот картинка и вопрос», сервер отвечает текстом и вероятностями.
- **Видеопамять (VRAM)** — память видеокарты; все нейросети должны в ней поместиться.

## 3. Один эпизод от начала до конца

**Эпизод** — одна попытка робота найти один предмет в одной квартире: старт в заданной точке, цель — категория
(здесь «кровать»), ограничение — 800 шагов.

### Этап 0. Подготовка (до того, как робот поедет)

**0.1. Квартира и робот.** Habitat-Sim загружает 3D-скан квартиры из набора HM3D и ставит робота в стартовую
точку эпизода.
- **Habitat-Sim** — симулятор: показывает, что увидела бы камера робота в этой квартире, и двигает робота.
- **HM3D** — набор 3D-сканов настоящих квартир.
- **navmesh** — сетка проходимых для робота мест (пол, где он помещается). Нужна симулятору, чтобы робот не
  проезжал сквозь стены, и раннеру, чтобы мерить кратчайшие пути. **Политика** (то, что принимает решения) navmesh
  не видит.

**0.2. Команда.** Из банка команд, написанных носителями языка, берётся команда для этого эпизода. Выбор зависит
только от номера эпизода, поэтому на казахском, kk_ru и английском у эпизода будет одна и та же по смыслу команда.
Пример: **«Төсекті тауып берші»** (kk), «Find the bed» (en).

**0.3. Разбор команды VLM (1 вызов).** Процесс робота отправляет серверу Qolda текст команды. Вместе с ним уходит
**промпт** — инструкция для модели. Промпт написан по-казахски и говорит примерно так: «Ты интерпретатор команд
домашнего робота. Ответь строго JSON по схеме: target — предмет в словарной форме; hypotheses — 3–5 английских
визуальных описаний с весами; rooms — где он обычно стоит». В промпте два примера ответа (зонтик и ведро).

Настоящий ответ Qolda на эту команду (из логов):

```json
{"target": "төсек",
 "hypotheses": [{"en": "bed with white sheets", "w": 0.5},
                {"en": "bed in a bedroom",      "w": 0.3},
                {"en": "bed with pillows",      "w": 0.2}],
 "rooms": ["bedroom"]}
```

- **target** «төсек» — что ищем, на языке команды. Пойдёт в вопрос проверки в конце.
- **hypotheses** — три способа описать кровать для детектора. **Веса** 0.5 / 0.3 / 0.2 — насколько модель верит
  каждому описанию. Сумма весов всегда 1.
- **JSON** — формат текста со строгой структурой, который программа может прочитать автоматически.

Если ответ не валиден (нет нужных полей, кириллица в гипотезах, сломан JSON), модели отправляется ошибка и просьба
исправить. Всего до 3 попыток. Если все провалились, эпизод сразу считается провалом «не понял команду».

**0.4. Сброс памяти.** Карта, кандидаты и вера в гипотезы обнуляются. Для эпизода создаётся **верификатор** —
объект, который будет спрашивать VLM «это төсек?», с порогом остановки этой модели (Qolda: 0.30).

### Этап 1. Осмотр на месте (первые 13 шагов)

Робот вращается на месте 1 рад/с: 13 шагов по 0.5 с ≈ полный оборот. На **каждом** шаге выполняется полный цикл
восприятия (этап 2) — робот сразу строит карту вокруг себя и высматривает кровать.

### Этап 2. Что происходит на каждом шаге (400–800 раз за эпизод)

Каждые 0.5 секунды симулированного времени:

```
 камера: цветной кадр RGB 640×480 + кадр глубины 640×480
   │
   ├─(А)─► карта занятости:     где стены, где свободно, что ещё не видели
   ├─(Б)─► SigLIP 2 → карта ценности:   «насколько этот вид похож на кровать» → в видимые клетки
   ├─(В)─► детектор × 3 гипотезы → рамки → SAM маски → 3D-точки → память кандидатов
   └─(Г)─► решение: крутиться / ехать к фронтиру / ехать к кандидату / повернуться к нему /
                     спросить VLM / СТОП
```

- **RGB-кадр** — обычная цветная картинка.
- **Кадр глубины** — картинка, где в каждом пикселе записано расстояние до поверхности в метрах. Камера глубины в
  реальности — как Intel RealSense D435.
- **Пиксель** — одна точка картинки; 640×480 = 307 200 пикселей.

**(А) Карта занятости.** Робот берёт каждый 4-й пиксель глубины (160×120 = 19 200 точек). Зная, где стоит камера и
куда смотрит, он переводит каждую точку в 3D-координаты комнаты. Затем смотрит на высоту точки:
- ниже 3 см — пол;
- от 3 до 19.5 см — **препятствие** (ножка стула, порог, плинтус): в это робот врежется;
- выше 19.5 см — проходимо: под столом робот проедет;
- ниже пола больше чем на 5 см — обрыв (лестница вниз), тоже препятствие.

Клетки карты вдоль луча от камеры до точки отмечаются как «скорее свободно», клетка с препятствием — как «скорее
занято». Подробно — в разделе 4.1.

**(Б) Карта ценности.** SigLIP 2 сравнивает **весь** кадр с тремя фразами: «a photo of a bed with white sheets.»,
«a photo of a bed in a bedroom.», «a photo of a bed with pillows.». Получаются три числа сходства; их взвешенная
сумма (с весами 0.5 / 0.3 / 0.2) — **ценность** этого вида. Она записывается во все клетки карты, которые сейчас
видит камера, сильнее в центре кадра и слабее у края. Так на карте копится ответ на вопрос «где пахнет кроватью».
Подробно — в разделе 4.3.

**(В) Поиск цели.** Детектор MM-GroundingDINO трижды смотрит на кадр, по разу на каждую гипотезу. Он выдаёт рамки,
у которых уверенность ≥ 0.5. Для каждой рамки:
1. **SAM 2** вырезает точный контур предмета внутри рамки;
2. пиксели маски с их глубиной превращаются в 3D-точки (точки ниже 5 см над полом отбрасываются);
3. если рядом (ближе 0.6 м) уже есть **кандидат**, точки добавляются к нему; иначе создаётся новый кандидат.

**Кандидат** — запись в памяти робота: «вот здесь, кажется, есть кровать»; у него есть положение, точки и
**уверенность**. После всех детекций кадра уверенность каждого кандидата обновляется: увидели снова — растёт,
должны были увидеть, но не увидели — падает. Подробно — в разделе 4.4.

**(Г) Решение.** Порядок вопросов, которые робот задаёт себе:
1. Ещё не закончил осмотр? → крутиться.
2. Есть **надёжный** кандидат (уверенность ≥ 0.45) ближе 0.6 м?
   - видно его в этом кадре → **спросить VLM** (этап 4);
   - не видно → повернуться к нему (до 8 шагов, потом считать «потерянным»).
3. Есть надёжный кандидат дальше? → **ехать к нему**: путь до свободного места не дальше 0.5 м от него.
4. Иначе → **ехать к лучшему фронтиру** (этап 3).
5. Фронтиров нет → теперь можно ехать и к «подозрительным» кандидатам (уверенность < 0.45).
6. Ехать некуда 5 раз подряд → эпизод окончен («не нашёл»).

### Этап 3. Исследование: куда ехать, пока кровати не видно

**Фронтир** — граница между уже изученной свободной областью и ещё не виденной. Буквально «край известного мира».
Если доехать до фронтира, камера увидит, что за ним.

На каждом шаге робот:
1. находит все фронтиры, до которых можно доехать;
2. для каждого берёт **ценность** с карты ценности (самое большое значение в радиусе 0.5 м);
3. считает **стоимость пути** до него планировщиком;
4. выбирает фронтир с наибольшим «ценность − 0.002 × стоимость»: перспективный и не слишком далёкий;
5. держится прежнего выбора, пока новый не лучше хотя бы на 0.005 (иначе робот метался бы).

Этот приём взят из **VLFM** (Vision-Language Frontier Maps, 2024): робот едет не просто к ближайшему неизвестному,
а туда, где «похоже на кровать», например в сторону спальни.

**Путь** строит **планировщик** (алгоритм Дейкстры, раздел 4.6) по карте занятости. Затем **контроллер** (pure
pursuit, раздел 4.7) за 5 тиков по 0.1 с превращает путь в скорости колёс. Через 0.5 с — новый кадр и новое
решение. Путь пересчитывается **каждый шаг**: карта всё время уточняется.

### Этап 4. Нашёл кандидата — подъехать и проверить

Допустим, на шаге 140 детектор нашёл рамку по гипотезе «bed in a bedroom» с уверенностью 0.62. SAM вырезал
кровать, точки легли в 3 м от робота, создан кандидат №5 с уверенностью 0.62 — он надёжный. Робот едет к нему.

Когда робот ближе 0.6 м к ближайшей точке кровати и видит её в кадре:
1. **кроп**: рамка кровати + 25% запаса по краям;
2. **вопрос VLM** на языке команды: «Суреттегі негізгі зат «төсек» болып табыла ма? Тек «иә» немесе «жоқ» деп
   жауап бер.» («Главный предмет на картинке — төсек? Ответь только «да» или «нет».»);
3. сервер возвращает не только ответ «иә», но и **вероятности первого токена**: например, «и» — 0.6, «ж» — 0.4.
   Отсюда **P(иә) = 0.6**;
4. **калибровка** переводит сырые 0.6 в честную вероятность: у Qolda 0.6 → 0.41;
5. сравнение с **порогом** 0.30 (подобран на dev): 0.41 ≥ 0.30 → **СТОП**;
6. если бы вышло меньше 0.25 → «это не кровать», кандидат отвергается навсегда, робот ищет дальше;
7. если между → «не уверена»: подъехать ближе и спросить ещё раз, когда кроп станет вдвое крупнее (до 3 вопросов).

- **Токен** — кусочек слова, которым оперирует модель. Модель генерирует ответ по токенам; у первого токена
  сервер отдаёт 10 самых вероятных вариантов с вероятностями.

Ответ проверки ещё и **сдвигает веса гипотез**: если кандидат, найденный по «bed in a bedroom», оказался кроватью,
вес этой гипотезы растёт, и дальше карта ценности и выбор кандидатов больше опираются на неё (раздел 4.5).

### Этап 5. Конец эпизода и оценка

Эпизод кончается, когда робот сказал «стоп», исчерпал 800 шагов, застрял больше 30 с или ему некуда ехать.

Затем раннер (программа, которая гоняет эпизоды) считает результат, используя «правду», которую робот не видел:
- **успех** — робот остановился, и кратчайший путь от него до ближайшей **точки обзора** кровати меньше 0.1 м.
  **Точка обзора** — место не дальше 1 м от предмета, откуда камера робота его видит (≥ 100 пикселей). Такие точки
  заранее посчитаны для камеры на высоте 0.15 м;
- **SPL** — успех с поправкой на длину пути: 1, если ехал кратчайшим путём; меньше, если петлял;
- **этап провала**, если не получилось: не понял команду / ни разу не увидел / видел, но детектор не нашёл /
  проверка отвергла настоящую кровать / остановился у чужого предмета / нашёл, но не доехал / застрял.

Всё это пишется одной строкой в `episodes.csv`, а каждое решение каждого шага — в `events.jsonl`.

## 4. Каждая часть подробно

### 4.1. Как строится карта занятости

**Что это.** Вид сверху на квартиру, разбитый на квадратики-**клетки** 5×5 см. Карта 40×40 м — это 800×800 клеток,
центр в точке старта. Про каждую клетку робот хранит одно число: насколько он уверен, что там препятствие.

**Почему не просто «занято / свободно».** Датчик шумит: одна точка может оказаться ошибкой. Поэтому робот копит
свидетельства. Удобнее всего копить их в **log-odds** (логарифм шансов):
- **вероятность** p — от 0 до 1 (0.8 = «80% что занято»);
- **шансы** = p / (1 − p): при p = 0.8 шансы 4 к 1;
- **log-odds** = ln(шансы): при p = 0.8 это 1.39; при p = 0.5 — 0; при p = 0.4 — −0.41.

Удобство в том, что новые свидетельства в log-odds просто **складываются**. «Увидел препятствие» = +0.85, «луч
прошёл насквозь» = −0.5. Значение ограничено ±3.5, чтобы карта могла переучиться, если что-то сдвинулось.

**Как обновляется клетка — пример.** Клетка в начале: 0 (p = 0.5, «не знаю»), помечена «ещё не видел».
- Кадр 1: в ней конец луча, точка на высоте 10 см (ножка стула) → +0.85 → 0.85 (p = 0.70). Ещё не «занята»:
  нужен порог 0.8 (log-odds 1.39);
- кадр 2: снова препятствие → 1.70 (p = 0.85) → **занята**. Двух независимых наблюдений хватает, одного — нет. Так
  одиночная ошибочная точка не «замуровывает» робота;
- если бы в кадре 2 луч прошёл сквозь неё → 0.85 − 0.5 = 0.35 (p = 0.59) → «неясно».

Клетка **свободна**, если p < 0.4 (log-odds < −0.41): одного «луча насквозь» (−0.5) хватает.

**Что считается препятствием — зависит от робота.** Высота точки над полом:

```
 0.195 м ─────────── выше: проходимо (робот проедет под столом)
          █ ПРЕПЯТСТВИЕ █   (ножки, пороги, плинтусы, низ дивана)
 0.03 м  ─────────── ниже: это пол
 0 м     ═══════════ ПОЛ
 −0.05 м ─────────── ниже: обрыв (лестница вниз, дыра) → тоже препятствие
```

Верх полосы = высота робота с камерой (16.5 см) + 3 см. У стандартного агента ростом 0.88 м полоса до 0.91 м, и
стол для него — препятствие.

**Лучи.** Для каждой из 19 200 точек кадра клетки по прямой от камеры до точки получают «−0.5» (там пусто: луч
прошёл). Конечная клетка получает «+0.85», если это препятствие, или «−0.5», если пол. Если точка выше полосы
(столешница), клетки по пути не трогаются: пол под столом не наблюдался.

**Пропавшие отражения.** Если пиксель смотрит вниз, а глубины нет (луч ушёл в пустоту — лестничный пролёт), робот
вычисляет, где луч пересёк бы пол, и ставит туда препятствие. Это аналог ИК-датчиков обрыва у настоящих пылесосов.

**Раздутие препятствий.** Робот — круг радиусом 17 см. Чтобы планировать путь его **центра**, препятствия на карте
«раздуваются» на 17 + 3 = 20 см: центр робота не должен заходить в раздутую зону.

### 4.2. Фронтиры — пример

```
 ? ? ? ? ? ? ?        ? — ещё не видели
 ? . . . F ? ?        . — свободно
 ? . R . F ? ?        # — препятствие
 # # . . . F ?        F — фронтир: свободная клетка рядом с «?»
 # # # . . . ?        R — робот
```

Соседние фронтирные клетки объединяются в одну «область фронтира». Области меньше 6 клеток (30 см) отбрасываются
как шум. Учитываются только те, до которых можно доехать.

### 4.3. Карта ценности — пример с числами

**SigLIP 2** — модель, которая переводит и картинку, и текст в **вектор** (список из сотен чисел) так, что
похожие по смыслу картинка и текст дают близкие векторы. Близость меряется **косинусным сходством**: 1 — одинаковое
направление, 0 — не связаны.

Пример (числа условные): кадр показывает дверной проём в спальню.

| гипотеза | вес | сходство кадра с «a photo of a …» |
|---|---|---|
| bed with white sheets | 0.5 | 0.08 |
| bed in a bedroom | 0.3 | 0.11 |
| bed with pillows | 0.2 | 0.07 |

Ценность кадра v = 0.5·0.08 + 0.3·0.11 + 0.2·0.07 = 0.087. Кадр с кухней дал бы, скажем, 0.05.

Эта ценность записывается во все клетки, которые камера видит в этом кадре, с **уверенностью** c, зависящей от
угла: в центре кадра c = 1, к краю падает до 0 (c = cos² угла, растянутого на половину поля зрения). Если у клетки
уже была ценность, новое значение смешивается со старым пропорционально уверенностям:

  новая ценность = (c_старая · v_старая + c · v) / (c_старая + c).

Так клетки, которые много раз видели «по центру», получают надёжное значение, а «краем глаза» — слабое.

### 4.4. Кандидаты: от пикселя до «здесь кровать»

**Из пикселя в 3D.** Камера описывается моделью **камеры-обскуры**: луч из центра камеры через пиксель (u, v) идёт
в направлении, которое задают **фокусное расстояние** fx ≈ 466 пикселей (следует из угла обзора 69°) и центр
кадра. Глубина говорит, на каком расстоянии вдоль этого луча поверхность. Получается точка (x, y, z) относительно
камеры. Матрица положения камеры переводит её в координаты квартиры.

**Из рамки в кандидата:**
1. SAM даёт маску — пиксели кровати внутри рамки;
2. пиксели маски с допустимой глубиной (до 4.5 м); если их меньше 50 — детекция отбрасывается;
3. отбрасываются точки ниже 5 см над полом. У камеры на 15 см рамка часто захватывает пол прямо перед роботом, и
   «ближайшая точка кровати» оказывалась у робота под носом — он останавливался сразу;
4. не больше 400 точек, случайная выборка;
5. центр точек ближе 0.6 м к существующему кандидату → это он же, добавляем точки; иначе — новый кандидат.

У кандидата хранится и **счёт по каждой гипотезе**: «по "bed in a bedroom" его видели с уверенностью 0.62, по "bed
with pillows" — 0.55». Это нужно, чтобы потом понять, какая гипотеза «сработала».

**Уверенность кандидата и «слияние по кадрам»** — пример:
- кадр 140: детекция 0.62 из 120 точек → уверенность 0.62, «объём» 120;
- кадр 141: снова 0.58 из 100 точек → (120·0.62 + 100·0.58)/220 = 0.60;
- кадр 142: кандидат должен быть виден (его точки в кадре и ничем не закрыты), но детектор его не нашёл →
  добавляется «0» с весом видимых точек, скажем 100 → (220·0.60 + 100·0)/320 = 0.41 → **ниже 0.45 → подозрительный**.

**Надёжный** кандидат (≥ 0.45) — к нему робот едет. **Подозрительный** — к нему едут, только когда фронтиры
кончились. Так базовая линия без VLM отсекает случайные ложные срабатывания (мелькнуло один раз и пропало).

Обратная сторона, найденная в D-065: настоящую кровать, увиденную один раз издалека, один промах вблизи (робот
подъехал, кровать видна частично, детектор не дал ≥ 0.5) делает подозрительной, и робот уезжает.

### 4.5. Гипотезы: зачем несколько и как меняются их веса

**Зачем несколько.** VLM не знает, как выглядит кровать в этой квартире, а детектор чувствителен к формулировке:
«bed with pillows» может найти кровать, которую «bed in a bedroom» пропустит. Несколько описаний — несколько
шансов.

**Где используются гипотезы (в трёх местах):**
1. **детектор** ищет каждую гипотезу отдельным проходом;
2. **карта ценности** — взвешенная сумма сходств по гипотезам;
3. **выбор кандидата** — уверенность кандидата × насколько он совпал с весомыми гипотезами.

**Как меняются веса (байесовское обновление).** «Байесовское» значит: старая вера × правдоподобие нового факта,
затем нормировка. Робот считает, что одна из гипотез — «правильный способ искать». Пример: кандидат найден в
основном по «bed in a bedroom», и VLM ответила «да, кровать» с высокой уверенностью. Значит, «bed in a bedroom»
скорее правильная → её вес растёт, например 0.3 → 0.42, остальные пропорционально уменьшаются. Если VLM сказала
«нет», вес гипотезы, которая привела к ложному кандидату, падает. Ниже 0.01 вес не опускается, чтобы одна ошибка
VLM не убила гипотезу навсегда.

### 4.6. Планировщик пути (алгоритм Дейкстры)

**Граф** — набор точек (вершин) и связей между ними (рёбер) с «ценой». Здесь вершины — клетки карты, рёбра — шаги
в 8 соседних клеток. Цена шага = длина × «неудобство» клеток:
- известная свободная клетка — 1;
- неизвестная — 1.5 (через неизвестное ехать можно, но рискованнее, поэтому дороже);
- рядом со стеной (ближе 30 см) — плюс до 1 (чтобы не тереться о стены);
- раздутые препятствия — нельзя.

**Алгоритм Дейкстры** находит самые дешёвые пути от робота **сразу до всех клеток** карты: он расходится от
старта волной, всегда продолжая с самой дешёвой ещё не обработанной клетки. Одного запуска хватает, чтобы
сравнить все фронтиры и всех кандидатов. Затем путь «спрямляется»: от каждой точки робот берёт самую дальнюю точку
пути, видимую по прямой без препятствий.

Если с запасом 3 см проехать нельзя (узкий проход, ножки стола), планировщик пробует ещё раз «впритык» — только с
радиусом робота.

### 4.7. Контроллер (pure pursuit) — как путь превращается в движение колёс

**Pure pursuit** («чистое преследование») — классический способ ехать по кривой: робот выбирает на пути точку в
20 см перед собой («морковка») и едет к ней по дуге, а морковка всё время убегает вперёд по пути.
- Если морковка сильно сбоку (больше 0.8 рад ≈ 46°) — сначала развернуться на месте.
- Иначе кривизна дуги k = 2·sin(угол на морковку) / 0.2 м, скорость до 0.3 м/с (медленнее у конца пути и на
  крутых поворотах), угловая скорость = k × скорость.
- Ограничитель не даёт разгоняться быстрее 0.5 м/с² и поворачивать резче 3 рад/с² — как у настоящих моторов.

У стандартного агента контроллера нет: он делает дискретные шаги «вперёд 25 см» или «поворот 30°».

### 4.8. Проверка и калибровка подробно

**Откуда P(yes).** Модель отвечает текстом «иә» или «жоқ». Но нам нужна не только буква, а уверенность. Сервер
отдаёт 10 самых вероятных **первых токенов** ответа. Казахские слова токенизатор режет по буквам, поэтому первый
токен — часто просто «и» или «ж». Пример из логов Qolda: «ж» — 0.97, «и» — 0.014. Тогда P(иә) = 0.014 / (0.014 +
0.97) ≈ 0.014: модель уверена, что это не цель. Для этого ответы обязаны начинаться с разных букв: иә / жоқ, да / нет,
yes / no.

**Зачем калибровка.** «Сырая» уверенность модели не равна реальной частоте. Например, Qwen часто говорит 0.98 про
чужие предметы, а Qolda говорит 0.3–0.5 про настоящие цели. **Калибровка** — пересчёт сырой уверенности в честную:
чтобы из ответов «0.4» правдой оказывались примерно 40%.

**Как подобрана (Platt scaling).** Формула p_честная = sigmoid(a · logit(p_сырая) + b), где logit(p) = ln(p/(1−p)),
а sigmoid — обратная к logit функция. Числа a и b подобраны на ~1100–1700 dev-ответах, где известна правда:
- **Qolda**: a = 0.51, b = −0.58. Сырые 0.27 → 0.25; 0.44 → 0.33; 0.60 → 0.41; 0.98 → 0.80;
- **Qwen**: a = 0.16, b = −1.41. Сырые 0.98 → 0.31; 0.9997 → ~0.48. Qwen почти всегда отвечает 0.999 или 0.001,
  поэтому её «0.98» мало что значит.

**Порог остановки** подобран на тех же данных так, чтобы лучше всего уравновесить пропуски и ложные остановки
(максимум F1): Qolda 0.30, Qwen 0.41.
- **F1** — среднее гармоническое точности (доля «стопов», которые были у настоящей цели) и полноты (доля настоящих
  целей, у которых робот остановился).

**Несколько взглядов.** Если робот спросил дважды (подъехал, кроп стал вдвое крупнее), ответы складываются в
log-odds относительно **базовой доли** (сколько процентов проверок в среднем приходится на настоящую цель: у
Qolda 21%). Второй и последующие ответы засчитываются с коэффициентом 0.5: два взгляда на один предмет — не два
независимых свидетельства.

**Ошибка, исправленная 15 октября (D-069).** Коэффициент 0.5 по ошибке применялся и к **первому** ответу. Из-за
этого один ответ Qolda должен был быть ≥ 0.42, а не ≥ 0.30, чтобы робот остановился, а второй вопрос почти
никогда не задавался. Теперь первый ответ засчитывается полностью, и порог работает так, как его подбирали.

### 4.9. Если робот упёрся или застрял

- **Нет прогресса**: 2 шага подряд команда «вперёд», а робот сдвинулся меньше чем на 3 см (упёрся в то, чего нет на
  карте, например в низкий порог) → 1 секунду назад и **виртуальное препятствие** на карте перед собой (круг 8 см),
  дальше путь в обход.
- **Обрыв** (датчики обрыва под бампером не видят пол) → назад и отметка на карте.
- **Застревание** дольше 30 секунд → эпизод окончен как «застрял».
- Стандартный агент: шаг «вперёд», который navmesh остановил, тоже отмечается как препятствие (D-063).

## 6. Чем отличаются варианты (плечи) эксперимента

Все варианты используют **одну и ту же** навигацию, карту, детектор, SAM и SigLIP. Отличаются только частями,
отмеченными ниже:

| вариант | что получает детектор | проверка перед стопом |
|---|---|---|
| без VLM («как VLFM») | английское название категории: «bed» | нет: стоп у первого надёжного кандидата рядом |
| Qolda / Qwen, kk / kk_ru / en | 3 гипотезы из разбора команды этой моделью | да, той же моделью, на языке команды |
| переводчик → Qwen | NLLB переводит команду на английский, Qwen разбирает английский текст | да, по-английски |
| без проверки | гипотезы VLM | нет |
| закрытый детектор (RT-DETR) | класс COCO «bed» | нет |
| идеальный детектор | правда из разметки сцены | нет — это потолок навигации |

**Плечо** (arm) — один вариант системы в эксперименте. Сравнения делаются **парно**: все плечи проходят одни и те же
эпизоды с одной и той же командой.

## 7. Словарь терминов

| термин | простое определение |
|---|---|
| **ObjectNav** | задача «найди объект такой-то категории в незнакомом помещении» |
| **zero-shot** | без обучения на этой задаче: система собрана из готовых моделей |
| **эпизод** | одна попытка: квартира, старт, цель, лимит шагов |
| **шаг (решения)** | один цикл «посмотрел → решил → поехал», 0.5 с у колёсного робота |
| **тик** | маленький шаг управления колёсами, 0.1 с; в одном шаге решения 5 тиков |
| **Habitat-Sim** | симулятор: рендерит, что видит камера робота, и двигает робота |
| **HM3D** | набор 3D-сканов настоящих квартир |
| **navmesh** | сетка мест, где робот может стоять и ехать; у политики её нет |
| **политика** | часть программы, которая принимает решения (куда ехать, когда остановиться) |
| **раннер** | программа, которая запускает эпизоды и считает результаты по «правде» |
| **RGB-D** | цветной кадр + кадр глубины (расстояние в каждом пикселе) |
| **камера-обскура** | простейшая модель камеры: луч из центра камеры через пиксель |
| **фокусное расстояние** | насколько камера «приближает»; у нас ≈ 466 пикселей |
| **карта занятости** | вид сверху из клеток 5 см: свободно / препятствие / неизвестно |
| **log-odds** | логарифм шансов; новые свидетельства в нём просто складываются |
| **раздутие препятствий** | расширение препятствий на радиус робота, чтобы планировать путь его центра |
| **фронтир** | граница известной свободной области с неизвестной |
| **карта ценности** | на каждой клетке — насколько вид оттуда «похож на цель» по SigLIP |
| **VLM** | нейросеть, понимающая картинки и текст (Qolda, Qwen3-VL) |
| **промпт** | текстовая инструкция для модели |
| **JSON** | строгий текстовый формат данных, читаемый программой |
| **гипотеза** | английское визуальное описание цели («bed with pillows») с весом |
| **вес гипотезы** | насколько система верит этому описанию; веса в сумме дают 1 |
| **токен** | кусочек слова, с которым работает языковая модель |
| **logprobs** | логарифмы вероятностей токенов, которые отдаёт сервер модели |
| **P(yes)** | вероятность ответа «да» на вопрос проверки |
| **открытый детектор** | ищет объекты по текстовому описанию (GroundingDINO) |
| **закрытый детектор** | знает только фиксированный список классов (RT-DETR, YOLO) |
| **рамка** (bounding box) | прямоугольник вокруг найденного объекта |
| **уверенность** (score) | число 0..1 у рамки: насколько детектор уверен |
| **SAM** | сегментатор: по рамке вырезает точный контур объекта |
| **маска** | картинка «объект / не объект» по пикселям |
| **SigLIP** | модель, переводящая картинки и тексты в сравнимые векторы |
| **вектор**, **косинусное сходство** | список чисел, описывающий смысл; сходство — насколько векторы сонаправлены |
| **кандидат** | запись в памяти: «здесь, вероятно, цель» с уверенностью |
| **надёжный / подозрительный** | кандидат с уверенностью ≥ 0.45 / ниже |
| **слияние по кадрам** | обновление уверенности кандидата: увидели — растёт, должны были увидеть, но нет — падает |
| **кроп** | вырезанный кусок кадра вокруг рамки |
| **верификатор / проверка** | вопрос VLM «это цель?» перед остановкой |
| **калибровка** | пересчёт сырой уверенности модели в честную вероятность |
| **Platt scaling** | способ калибровки: sigmoid(a·logit(p) + b) |
| **порог остановки** | минимальная честная уверенность, при которой робот останавливается |
| **базовая доля** | доля настоящих целей среди всех проверок в калибровочных данных |
| **байесовское обновление** | старая вера × правдоподобие нового факта, затем нормировка |
| **алгоритм Дейкстры** | поиск самых дешёвых путей от одной клетки до всех остальных |
| **pure pursuit** | следование по пути к точке на 20 см впереди по дуге |
| **точка обзора** | место не дальше 1 м от цели, откуда её видно; стоп в 0.1 м от неё — успех |
| **SR** (success rate) | доля успешных эпизодов |
| **SPL** | успех с поправкой на длину пути |
| **этап провала** | на каком шаге конвейера эпизод сломался |
| **плечо** | один вариант системы в эксперименте |
| **dev / test** | dev — тренировочные квартиры для настройки; test — отдельные квартиры только для итоговых цифр |
