# Как работает код kznav — подробный разбор к защите

Документ объясняет весь стенд сверху вниз: зачем он нужен, из каких слоёв состоит, как идёт один шаг робота, что
делает каждая важная функция и почему выбраны именно такие числа. В конце — шпаргалка параметров и список вероятных
вопросов на защите с ответами.

Как читать: разделы 1–3 дают общую картину (их достаточно, чтобы рассказать архитектуру за 5 минут), разделы 4–10
идут по слоям кода, раздел 13 — шпаргалка чисел, раздел 14 — вопросы. Ссылки вида `kznav/policy/objectnav.py:109`
указывают файл и строку. Номера решений `D-0xx` — записи в `docs/decisions.md`, где каждое решение обосновано цифрами.

## 1. Задача в одном абзаце

**Zero-shot ObjectNav по команде на казахском.** Робот-пылесос оказывается в незнакомой квартире (3D-скан HM3D в
симуляторе Habitat-Sim) и получает команду вроде «Төсекті тауып берші» («найди кровать»). Он должен доехать до
кровати и сказать «стоп» не дальше 0.1 м от точки, откуда кровать видна. «Zero-shot» значит: ничего не обучается на
этой задаче — система собрана из готовых предобученных моделей (VLM, детектор, сегментатор, CLIP-подобный энкодер),
а навигация — классическая (карта, фронтиры, планировщик).

**Научный вопрос статьи:** где и почему ломается такая навигация, когда команда на казахском, и помогает ли родная
казахская VLM (Qolda-4B) по сравнению с обычной мультиязычной того же размера (Qwen3-VL-4B). Гипотезы:

| | гипотеза | чем проверяется в коде |
|---|---|---|
| H1 | потеря от казахского возникает на стыке «язык → зрение» (запрос, детекция, проверка), а не в навигации | разложение разрыва SR(en) − SR(kk) по этапам провала (`kznav/eval/paper.py: gap_decomposition`) |
| H2 | для культурных предметов (қазан, сандық…) разрыв больше; перевод его увеличивает | культурная часть: фото-бенчмарк и 3D-вставки (`kznav/eval/photo_bench.py`) |
| H3 | родная модель сокращает казахский разрыв; на английском она не лучше | Qolda kk против Qwen kk и взаимодействие с языком (контрасты C1, C2) |
| H4 | проверка VLM перед остановкой повышает успех, но ей нужна калибровка | с проверкой против без (C4), ECE до/после калибровки |

## 2. Архитектура сверху

### 2.1. Конвейер (что происходит с командой)

```
 команда (kk / kk_ru / en)
        │
        ▼
 ┌──────────────────────┐   один раз за эпизод (кэшируется)
 │ VLM: разбор команды  │── target «төсек» + 3–5 английских гипотез с весами:
 │ (parse_goal)         │   например "double bed" 0.5, "bed with pillows" 0.3, "bedroom bed" 0.2
 └──────────────────────┘
        │ гипотезы = текстовые запросы
        ▼
 ┌──────────────────────────────────── каждый шаг решения (0.5 с симуляции) ───────────────┐
 │ RGB-D кадр 640×480 ─► карта занятости (глубина)                                          │
 │                   ├─► карта ценности (SigLIP 2: «похоже ли то, что я вижу, на цель?»)    │
 │                   └─► детектор MM-GroundingDINO (по гипотезам) ─► SAM 2 маска ─► 3D-точки │
 │                                            ─► память кандидатов (слияние по кадрам)       │
 │ решение: осмотреться / ехать к фронтиру / ехать к кандидату / повернуться к нему /       │
 │          спросить VLM «это кровать?» (verify_candidate) / СТОП                           │
 └──────────────────────────────────────────────────────────────────────────────────────────┘
        │ путь в координатах карты
        ▼
 исполнитель: pure pursuit → (v, w) колёс  |  или дискретные действия стандартного агента
        │
        ▼
 Habitat-Sim: робот двигается, новый кадр
```

Это архитектура **VLFM** (Yokoyama et al., 2024): фронтиры + карта ценности из vision-language модели + открытый
детектор. Наши добавки: (1) VLM превращает команду на любом языке в английские визуальные гипотезы с весами;
(2) VLM проверяет кандидата перед остановкой, и её ответ откалиброван; (3) слияние уверенности кандидатов по кадрам
(как в ApexNav, 2025) и маски SAM; (4) всё это для низкого колёсного робота с камерой на 0.15 м.

**Почему модульная система, а не одна большая модель (end-to-end)?** (а) Можно измерить, где именно ломается
(H1) — у каждого модуля свой выход, который сравнивается с правдой из разметки сцены. (б) VLM зовётся редко
(~3–5 раз за эпизод), а детектор — на каждом шаге; VLM на каждом кадре была бы в 10–20 раз медленнее. (в) Детектор
общий для всех вариантов, поэтому разница между Qolda и Qwen — это разница в понимании языка.

### 2.2. Слои кода

```
configs/   все числа системы (Hydra YAML). В коде чисел-настроек нет.
prompts/   версии промптов (parse_goal v1/v2, verify_candidate v1, describe v1); хэш каждого пишется в логи
lexicon/   словари категорий (какие слова считаются названием «кровати» на kk/ru/en)
commands/  банк команд, написанных носителями (dev / test)
kznav/
  sim/         симулятор: обёртка Habitat, роботы, движение, шумы, локализация, датасет, точки обзора
  perception/  камера, карта занятости, фронтиры, карта ценности, детекторы, SAM, память кандидатов
  policy/      решения робота, планировщик, контроллер, проверка VLM, байесовская вера, калибровка
  language/    контракт VLM, бэкенды (Qolda, Qwen, mock, replay), разбор команды, промпты, logprobs, перевод
  run/         один эпизод (run_episode), прогон по датасету (BenchmarkRunner), логи, манифест
  eval/        метрики habitat-lab, исходы и этапы провала, статистика, таблицы статьи, мощность
  report/      видео эпизодов и графики
servers/   FastAPI-серверы Qolda и Qwen3-VL (OpenAI-совместимый API, logprobs)
tools/     командные утилиты: run_eval, run_matrix, fit_calibration, make_split, check_hm3d, ...
paper/     матрицы прогонов (какие плечи с какими настройками) и спецификации таблиц
tests/     435 тестов (pytest), большая часть без GPU — на аналитическом mock-симуляторе
```

**Правило зависимостей:** `sim` ничего не знает о политике; `perception` не знает о языке; `policy` не видит
navmesh и разметку сцены (кроме явно включённого «идеального детектора»-абляции); всё «привилегированное» (правда
о том, где цель) живёт в `run/episode.py` и `eval/` и используется только для метрик и меток.

### 2.3. Один шаг решения — поток данных

1. `HabitatEnv.observe()` → `Observation(rgb, depth, semantic, pose, position, camera_transform, sim_time)`.
2. Локализатор пересчитывает наблюдение в «оценённую» систему координат робота (по умолчанию — истинная поза).
3. `ObjectNavPolicy.step(obs)`:
   1. карта занятости обновляется по глубине;
   2. карта ценности обновляется по SigLIP-оценке всего кадра;
   3. детектор ищет гипотезы в кадре → SAM даёт маски → точки маски переводятся в 3D → кандидаты в памяти
      создаются/обновляются → в конце кадра уверенность кандидатов сливается;
   4. `_decide()` выбирает действие (`Decision`).
4. `Executor.execute(decision)` превращает решение в движение: 5 тиков управления по 0.1 с (колёсный робот) или
   одно дискретное действие (стандартный агент).
5. Раннер считает привилегированные вещи: видна ли цель (по семантике), попал ли детектор в цель, что ответил
   верификатор про настоящую цель; пишет событие в `events.jsonl`.
6. Повтор до `stop`, лимита шагов (800 для колёсного, 500 для стандартного), застревания или «некуда ехать».

## 3. Конфигурация (Hydra) и реестры

### 3.1. Как собирается конфиг

`configs/config.yaml` — корень. В `defaults` перечислены группы, в каждой выбирается один файл:

| группа | по умолчанию | варианты |
|---|---|---|
| embodiment | wheeled_vacuum | wheeled_vacuum_kinematic, habitat_agent |
| dataset | hm3d_objectnav_v1_val | …_train (dev), …_valmini (smoke), debug_ycb |
| backend | mock | qolda, qwen3vl_4b, replay |
| perception | default | — |
| detector | mm_grounding_dino_base (D-064) | none, oracle_semantic, grounding_dino_tiny, rtdetr_coco |
| segmenter | sam2_tiny | box |
| value_encoder | none | siglip2_base |
| goal | multi | top1, mt_word, mt_command |
| policy, eval | default | — |

Переопределения пишутся в командной строке: `backend=qolda detector=oracle_semantic
policy.stop.calibration_file=calib/qolda_dev.json`. `kznav/run/config.py: compose_config()` собирает итоговый
словарь и раскрывает интерполяции (`${paths.data_root}`).

**Почему так:** любой эксперимент = набор переопределений, записанный в матрицу (`paper/matrices/*.yaml`). Код
не меняется между плечами. Итоговый конфиг целиком пишется в `manifest.json` прогона вместе с его SHA-256
(`kznav/run/manifest.py: config_hash`). При продолжении прогона (`--resume`) хэш сравнивается: если конфиг
изменился, продолжение запрещено (`tools/run_eval.py`), чтобы в одной ячейке не смешались разные настройки.

### 3.2. Реестры компонентов

`kznav/registry.py: Registry` — словарь «имя → класс». Компонент регистрируется декоратором
`@DETECTORS.register("grounding_dino")` и выбирается в конфиге полем `type: grounding_dino` (или `class_path:
пакет.модуль:Класс` для внешнего кода). Так устроены детекторы, сегментаторы, энкодеры ценности
(`perception/base.py`), VLM-бэкенды (`language/registry.py`), модели шума (`sim/noise.py`), переводчики.
Добавить новую модель = новый файл конфига + класс; навигационный код не трогается.

## 4. Симулятор, роботы и эпизоды (`kznav/sim/`)

### 4.1. Что такое Habitat-Sim и HM3D

- **Habitat-Sim** — симулятор Meta AI: загружает 3D-скан квартиры (`.glb`), рендерит RGB, глубину и семантику с
  виртуальной камеры, считает **navmesh** (сетку проходимых поверхностей, алгоритм Recast) и геодезические
  расстояния по ней (кратчайший путь по проходимой поверхности, а не по прямой).
- **HM3D** (Habitat-Matterport 3D) — сканы реальных квартир. **HM3D ObjectNav v1** — стандартный набор эпизодов:
  стартовая точка, категория цели (одна из 6: chair, bed, plant, toilet, tv_monitor, sofa) и экземпляры цели с
  «точками обзора». val: 2000 эпизодов в 20 сценах; train: 80 сцен (из них наши dev-выборки).
- **Семантический сенсор** рисует в каждом пикселе id экземпляра объекта. Политика его **не видит**: он нужен
  только раннеру для меток (видна ли цель, попал ли детектор в цель) и для «идеального детектора»-абляции.

### 4.2. Системы координат (`frames.py`)

Две системы, и путать их нельзя:

| | Habitat (3D) | карта (2D) |
|---|---|---|
| оси | +Y вверх, «вперёд» неповёрнутого агента = −Z, +X вправо | x_map = x_h, y_map = −z_h |
| курс | кватернион | yaw против часовой от +x_map; неповёрнутый агент имеет yaw = +π/2 |

Функции: `habitat_to_map(p) = (p[0], −p[2])`, `map_to_habitat(x, y, h) = (x, h, −y)`, `yaw_from_quat` (курс оси
−Z тела), `quat_from_yaw(yaw)` (поворот вокруг +Y на yaw − π/2), `wrap_angle` (в [−π, π)).

### 4.3. Два «тела» робота (embodiment)

| | колёсный робот-пылесос | стандартный агент Habitat |
|---|---|---|
| конфиг | `embodiment/wheeled_vacuum[_kinematic].yaml` | `embodiment/habitat_agent.yaml` |
| тело | цилиндр Ø0.34 м, высота 0.12 м | цилиндр r = 0.18 м, высота 0.88 м |
| камера | 0.15 м над полом, 0.14 м вперёд, **наклон 20° вверх**, hfov 69°, 640×480, глубина 0.2–5 м | 0.88 м, без наклона, hfov 79°, глубина 0.5–5 м |
| движение | непрерывное: v ≤ 0.3 м/с, ω ≤ 1.5 рад/с, ускорения 0.5 м/с² и 3 рад/с² | дискретное: вперёд 0.25 м, поворот 30° |
| navmesh | пересчитан под робота: радиус 0.17, высота 0.17, подъём 1 см, клетка 2.5 см | из датасета (агент 0.88 м) |
| лимит эпизода | 800 решений по 0.5 с (выбрано на dev, D-005) | 500 действий (стандарт habitat-lab) |
| где используется | **главная таблица (б)** | таблица (а) — сравнение с литературой (VLFM) |

Почему два тела (D-001): опубликованные числа (VLFM 52.5%) получены на стандартном агенте. Наш робот низкий: он
проезжает под столами, не видит то, что стоит на столе, не берёт пороги выше ~1 см. Его числа несравнимы с
литературой, поэтому тот же конвейер прогоняется и на стандартном агенте.

Наклон камеры 20° выбран на dev с идеальным детектором (D-004): успех 77.6% против 65.8% при 0° и 36.8% при 30°.
Камера в 15 см у пола без наклона видит в основном пол и ножки мебели.

### 4.4. Как движется колёсный робот: два режима

`HabitatEnv.__init__` (`env.py:76`) смотрит на `embodiment.physics.mode`:

- **articulated** (`sim/robot.py: WheeledRobot`): робот — URDF-модель (`sim/urdf.py: build_urdf`) в физическом
  движке Bullet: шасси, два ведущих колеса с моторами по скорости (момент ≤ 0.4 Н·м), передний и задний ролики.
  Команда (v, ω) → скорости колёс (`wheel_speeds`): ω_л = (v − ω·b/2)/r, ω_п = (v + ω·b/2)/r, где b = 0.23 м —
  база, r = 0.035 м — радиус колеса. Движение — то, что посчитала физика: проскальзывание, упоры и застревания не
  программируются. Шаг физики 1/240 с, управление 10 Гц.
- **kinematic** (`sim/kinematic.py: KinematicBase`, D-053): те же размеры, камера и ограничения скорости, но без
  физики. Каждый тик: ограничитель скоростей → (опционально) шум исполнения → точная интеграция модели
  «одноколёсного» робота → шаг по navmesh `pathfinder.try_step(start, target)`. Робот скользит вдоль стен и не
  может покинуть navmesh. Если результат отличается от цели больше чем на 1 мм, тик помечен как столкновение.

**Почему главная таблица в кинематике (D-052, D-053).** Сканы HM3D физически неточны: дыры, бугристый пол, мягкие
края ступеней. С физикой робот застревал на артефактах скана, и таблица мерила бы сетку, а не метод. Физика
оставлена для исследования устойчивости.

`diff_drive.py`:
- `VelocityLimiter.step(v_cmd, w_cmd, dt)`: обрезать до максимумов скорости, затем ограничить изменение за dt
  ускорением (Δv ≤ a_max·dt);
- `integrate_unicycle(x, y, yaw, v, w, dt)`: точное интегрирование при постоянных (v, ω). При ω ≈ 0 — прямая;
  иначе дуга радиуса R = v/ω: x' = x + R·(sin(yaw + ω·dt) − sin yaw), y' = y − R·(cos(yaw + ω·dt) − cos yaw).

### 4.5. Обёртка `HabitatEnv` (`env.py`)

| метод | что делает |
|---|---|
| `__init__` | создаёт симулятор с сенсорами RGB / Depth / Semantic, настраивает navmesh (`_setup_navmesh`: из датасета или пересчёт по параметрам тела), создаёт робота нужного режима |
| `reset(position, yaw)` | ставит робота на старт эпизода; физическому даёт 0.25 с «осесть» на колёса |
| `drive(v, w, n)` | колёсный робот: n тиков управления; на каждом `Tick(t, pose, position, v, w, collision, tilt, odom_twist, cliff)` |
| `act(action)` | стандартный агент: `move_forward` / `turn_left` / `turn_right`; `collision` = navmesh остановила шаг |
| `observe()` | ставит камеру в оптический центр, рендерит, добавляет шум глубины, возвращает `Observation` |
| `camera_transform_at(pos, yaw)` | матрица камеры «если бы робот стоял здесь»: поворот вокруг Y, наклон вокруг X, смещение 0.15 м вверх и 0.14 м вперёд |
| `render_at(pos, yaw)` | отрисовка с гипотетической позы без перемещения робота (нужна для точек обзора) |
| `geodesic_distance(start, goals)` | кратчайший путь по navmesh до ближайшей из целей; ∞, если недостижимо |
| `snap(point)` | ближайшая точка navmesh |
| `semantic_objects()` | экземпляры из разметки сцены: id, категория, AABB (ограничивающий параллелепипед) |

### 4.6. Шумы и локализация (исследование устойчивости, D-051)

По умолчанию все шумы выключены (`noise.*.model: none`). У каждой модели свой генератор случайных чисел, он
пересевается на каждый эпизод (`reseed_noise_models`), поэтому шум эпизода зависит только от seed прогона и id
эпизода.

- **Глубина `redwood`** (`noise.py: redwood_simulate`): модель шума реальной RGB-D камеры (Redwood / CLAMS), как в
  habitat-sim, но переписанная на numpy со своим генератором: у habitat-sim глобальный ГСЧ ломал бы детерминизм.
  Дрожание пикселей, прореживание 2×2, искажение глубины по измеренной таблице, шум в диспарантности.
- **Исполнение `gaussian_twist`**: реальная скорость = v·(1 + e_v) и ω·(1 + e_w) + b_w; ошибки держатся 0.5 с,
  потом пересэмплируются (ошибка мотора, неровный пол).
- **Дрейф одометрии `gaussian_increment`**: к каждому приращению добавляются ошибка масштаба 2%, боковой шум 1 см
  на метр, ошибка поворота 2% и дрейф курса 1° на метр.
- **Локализация** (`localization.py`). `ground_truth`: политика получает истинную позу, как GPS + компас в
  стандартном ObjectNav. `odometry`: поза интегрируется из скоростей колёс от известного старта через модель
  дрейфа. `frame_correction` строит матрицу, переводящую истинную позу в оценённую, и применяет её к камере, так что
  карта, кандидаты и пути живут в «плывущей» системе робота. Метрики всегда считаются по истинной позе.

### 4.7. Датасет и эпизоды

`objectnav_dataset.py` читает файлы habitat-lab без самой habitat-lab:
- `val.json.gz` + `content/<сцена>.json.gz`; эпизоды сцены ссылаются на общий список целей
  (`goals_by_category`), он разбирается один раз на сцену (в train ~50 тыс. эпизодов на сцену);
- **`episode_id = "<сцена>:<номер в файле>"`** — уникален во всём наборе и не зависит от выборок и продолжений;
- `stable_index(key, n)` = SHA-256(key) mod n — детерминированный «случайный» выбор: какая команда достанется
  эпизоду, у каких эпизодов пишется видео. Не зависит от порядка и подмножества.

`episodes.py`:
- `ObjectNavEpisode`: старт, курс, категория, список `GoalInstance` (id, семантический id, AABB, точки обзора),
  `start_geodesic_m` — кратчайший путь до ближайшей точки обзора по navmesh **оцениваемого** тела;
- `footprint_distance(p, aabb)`: горизонтальное расстояние от точки до «следа» объекта на полу (0 внутри);
- **`compute_view_points`** — ключевая функция для низкого робота (D-001, D-056). Точки обзора — позиции, остановка
  в которых считается успехом. В датасете они посчитаны для агента 0.88 м, а для камеры на 0.15 м они другие: со
  стула видно сиденье, с пола — ножки. Алгоритм:
  1. сетка с шагом 0.1 м вокруг следа объекта в пределах 1 м;
  2. каждая точка прижимается к navmesh робота (не дальше 5 см);
  3. проверка, что это пол под объектом (объект может висеть до 2 м выше — ТВ на стене);
  4. камера разворачивается на центр объекта, `render_at`;
  5. если в семантике видно ≥ 100 пикселей этого экземпляра, точка — точка обзора.

  Шаг сетки должен быть ≤ 0.1·√2 м, иначе успех зависел бы от сетки, а не от робота.

`run/benchmark.py: prepare_episode` готовит эпизод для тела или **исключает** его с причиной:

| причина | когда |
|---|---|
| `goal_not_in_scene` | id цели не найден в разметке, или позиция цели дальше 0.5 м от центра AABB (ошибка сопоставления) |
| `no_view_points` | с высоты робота цель не видна ни из одной точки |
| `start_off_navmesh` | старт дальше 0.2 м от navmesh робота или на другом этаже (больше 0.3 м по высоте) |
| `unreachable` | от старта до точек обзора нет пути |
| `start_at_goal` | старт уже в точке обзора |

Исключения пишутся в `exclusions.csv` и всегда показываются в отчётах. Для выборок колёсного робота эпизоды заранее
отфильтрованы по проходимости (`tools/check_hm3d.py` → `make_split.py --runnable`, D-052). Пересчитанные точки
обзора кэшируются по хэшу всех параметров, от которых они зависят (`ViewPointCache`).

`mock_env.py: MockEnv` — аналитический мир из параллелепипедов с тем же интерфейсом, что у `HabitatEnv`: глубина и
семантика считаются лучами точно, геодезика — алгоритмом Дейкстры по сетке. Нужен для тестов без GPU; его числа —
не результат.

## 5. Восприятие (`kznav/perception/`)

### 5.1. Камера (`camera.py`)

Модель «камера-обскура», совпадающая с сенсором Habitat:
- фокусное расстояние из угла обзора: **fx = fy = (W/2) / tan(hfov/2)**. У робота W = 640, hfov = 69° → fx ≈ 465.6 px;
- центр кадра (cx, cy) = (W/2, H/2), центры пикселей в (u + 0.5, v + 0.5);
- глубина Habitat **плоская** (вдоль оптической оси, не расстояние до точки);
- `backproject(depth, K, v, u)`: пиксель → точка в системе камеры: x = (u + 0.5 − cx)/fx·z, y = −(v + 0.5 − cy)/fy·z,
  точка = (x, y, −z) (камера смотрит вдоль −Z);
- `to_world(p, T)`: в мировую систему матрицей камеры 4×4; `project`: обратная операция (нужна для проверки
  видимости кандидатов).

### 5.2. Карта занятости (`occupancy.py: OccupancyMap`)

Квадрат 40×40 м с центром в старте, клетка 5 см (800×800 клеток). В каждой клетке — **log-odds** (логарифм шансов)
того, что она занята.

**Какие точки — препятствия зависит от тела** (`classify_points`). Высота точки над полом h:
- h < h_min → пол; h_min = max(0.03 м, подъём navmesh);
- h_min ≤ h ≤ h_max → **препятствие**; h_max = верх тела + 0.03 м (колёсный: 0.165 + 0.03 = 0.195 м; стандартный
  агент: 0.91 м);
- h > h_max → проходимо (столешница для низкого робота — не препятствие: он проедет под столом);
- h < −0.05 м (ниже пола) → препятствие: обрыв, ступень вниз, дыра скана. Это аналог ИК-датчиков обрыва пылесоса;
  только для колёсного робота (D-026). Стандартный агент ходит по лестницам, для него это не препятствие (D-052).

**Обновление за кадр** (`update`, `update_from_points`):
1. берётся каждый 4-й пиксель (160×120 лучей), глубина ≤ 4.5 м;
2. точки → мир → категория;
3. клетки вдоль луча от камеры до точки-пола или точки-препятствия получают «промах» (−0.5): там пусто;
4. конечная клетка: препятствие → «попадание» (+0.85), пол → «промах»;
5. если в одном кадре клетка и «попадание», и «промах» — побеждает попадание (нижние точки стены похожи на пол);
6. лучи к точкам выше полосы ничего не очищают: пол под ними не наблюдался;
7. **пропавшие отражения** (D-031): пиксель, смотрящий вниз без глубины там, где должен быть пол (ближе 1.5 м), —
   это провал (лестница вниз, край скана). Точка пересечения его луча с плоскостью пола становится препятствием.

**Пороги.** log-odds ограничены ±3.5. Занята, если вероятность > 0.8 (logit 1.386 → нужно 2 попадания: 0.85·2 = 1.7);
свободна, если < 0.4 (logit −0.405 → хватает одного промаха). «Попадание, потом промах» даёт 0.35 → p = 0.59 →
неизвестно. Так одиночные шумные точки не замуровывают робота (D-019).

`mark_free_disk` — клетки под самим роботом свободны (камера под себя не видит). `mark_obstacle_disk` — виртуальное
препятствие (робот упёрся во что-то, чего нет на карте). `inflated_obstacles(r)` — препятствия, «раздутые» на
радиус робота: центр робота не должен заходить в такие клетки.

### 5.3. Фронтиры (`frontiers.py`)

**Фронтир** — свободная клетка, граничащая с неизвестной (4-связность). Только фронтиры, достижимые от робота
(связная компонента свободного пространства без раздутых препятствий — `reachable_mask`), группируются в области
(8-связность); область меньше 6 клеток отбрасывается. Каждая область представлена клеткой, ближайшей к её
центроиду, чтобы цель сама лежала на фронтире. Исследование = «ехать к фронтиру, пока неизвестное не кончится».

### 5.4. Карта ценности (`value_map.py`, `siglip.py`) — идея VLFM

Отвечает на вопрос «куда ехать, когда цели ещё не видно». На каждом кадре **SigLIP 2** (google/siglip2-base) считает
косинусное сходство всего изображения с текстом «a photo of a {гипотеза}.» для каждой гипотезы. Ценность кадра
**v = Σ_k w_k·s_k** (веса гипотез из разбора или из байесовской веры).

Эта ценность записывается во все клетки, видимые в кадре, с уверенностью, падающей к краю поля зрения:
**c = cos²(угол от оптической оси / (hfov/2) · π/2)** — в центре 1, на краю 0. Слияние со старым значением —
взвешенное среднее: v ← (c_old·v_old + c·v)/(c_old + c), c ← (c_old² + c²)/(c_old + c).

Выбор фронтира (`objectnav.py: _choose_frontier`): **оценка = max ценности в радиусе 0.5 м − 0.002 × стоимость
пути**. С гистерезисом 0.005: робот держится прежней цели, пока другая не лучше заметно, иначе он метался бы.
Без энкодера ценности — ближайший фронтир. В отличие от VLFM, у нас SigLIP 2 вместо BLIP-2.

### 5.5. Детектор MM-GroundingDINO (`grounding_dino.py`)

**GroundingDINO** — открытый детектор: на вход картинка и текст «chair .», на выход рамки с уверенностью, что в
рамке то, что описано текстом. Используется **MM-GroundingDINO base** (Swin-B, обучен на Objects365, GoldG, V3Det;
веса `openmmlab-community/mm_grounding_dino_base_o365v1_goldg_v3det`). Важные настройки:

| настройка | значение | почему |
|---|---|---|
| `box_threshold` | 0.50 | выбран на dev (D-060); ниже — больше ложных, выше — пропуски |
| `text_threshold` | 0.25 | порог совпадения слов фразы |
| `query_mode: separate` | каждая гипотеза — отдельная подпись и отдельный проход сети | совместная подпись «q1 . q2 . q3 .» на кадрах низкой камеры различала цель не лучше случайного (AUROC 0.55 против 0.61; D-058) |
| `input_resize: native` | кадр 640×480 как есть | стандартное растяжение до 800 по короткой стороне в 1.7 раза медленнее и не точнее (D-059) |
| `max_box_area_frac` | 0.8 | рамка больше 80% кадра отбрасывается: вблизи стены детектор «находит» цель во всём кадре (D-054) |

Почему этот детектор: на кадрах робота он на 7.5 п. лучше GroundingDINO-tiny по TPR при FPR 10% (D-060), а
закрытый COCO-детектор RT-DETR — хуже (0.26 против 0.42; D-062).

Изображение предобрабатывается один раз, потом цикл по подписям. `match_query` (сходство Жаккара по токенам)
связывает фразу, которую выдала модель, с запросом; фраза без общих слов отбрасывается. Каждая детекция —
`Detection(box, score, query_index, phrase, mask=None)`.

Другие детекторы:
- `coco_detector.py` — **RT-DETR R101** (закрытый, 80 классов COCO, порог 0.8 как у VLFM) для строки «VLFM с
  закрытым детектором» (D-062). Языка не понимает: категория отображается в класс COCO (`sofa → couch`).
- `oracle.py` — **идеальный детектор**: берёт пиксели цели из семантического сенсора, уверенность 1.0, маска
  точная. Это абляция-потолок: показывает, сколько может навигация, если всё видеть правильно.
- `mock.py` — `none` (ничего не находит), `box` (маска = рамка), `hash` (псевдо-энкодер для тестов).

### 5.6. Маски SAM 2 (`sam.py`)

Рамка детектора содержит и объект, и фон (стену за стулом, пол перед ним). Если ставить кандидата по всей рамке,
его 3D-положение уезжает. **SAM 2.1-tiny** получает рамку как подсказку и возвращает маску ровно по контуру
объекта. Кадр кодируется один раз (`get_image_embeddings`), затем каждая рамка декодируется в маску; маска
обрезается по рамке; меньше 20 пикселей → `None` → используется сама рамка. `precise = True` говорит памяти
кандидатов, что фон уже убран.

### 5.7. Память кандидатов (`objects.py: ObjectMemory`) — где «находится» цель

**Локализация детекции** (`localize`):
1. пиксели маски с правильной глубиной (≤ 4.5 м); меньше 50 → детекция отбрасывается;
2. фильтр пола: точки ниже 5 см над полом убираются (у низкой камеры рамка достаёт до пола перед роботом, и
   «ближайшая точка объекта» оказывалась на полу у самого робота — робот сразу останавливался, D-054);
3. только для масок-рамок: остаётся передний слой (глубина в пределах 0.5 м от ближайших 5%), а не стена позади;
4. не больше 400 случайных точек → перевод в мир.

**Слияние в кандидатов** (`_merge`). Детекция, у которой медиана точек ближе 0.6 м к существующему кандидату,
обновляет его, **какая бы гипотеза её ни дала**: кандидат — это один физический предмет. Обновляется позиция
(среднее), точки следа, лучший счёт, **счёт по каждой гипотезе** `scores[query_index]` (для байесовского
обновления), последняя рамка (для кропа проверки).

**Слияние уверенности по кадрам** (`end_frame`, D-060, как в ApexNav). У кандидата есть уверенность `conf` и «объём»
`volume` (сколько точек её подтверждало). В конце каждого кадра:
- если кандидат обнаружен в кадре: `conf ← (volume·conf + n·score)/(volume + n)`, где score — лучший счёт этого
  кадра, n — число точек детекции (не больше 200);
- если не обнаружен, **но должен был быть виден** (≥ 20 его сохранённых точек попадают в кадр, ближе 4.5 м и не
  закрыты другим объектом с допуском 0.3 м — `visible_points`): то же обновление со score = 0 (отрицательное
  свидетельство), `misses += 1`;
- если не виден (за спиной, закрыт) — ничего не меняется.

**Надёжные и подозрительные.** Кандидат с `conf ≥ 0.45` — **надёжный**: к нему робот едет. Ниже — **подозрительный**:
к нему едут, только когда фронтиры кончились (`exhausted`). Порог 0.45 выбран на dev для базовой линии без VLM
(D-060): 0.30 давал больше ложных остановок, 0.60 — больше эпизодов с исчерпанным лимитом.

Найденный в D-065 эффект: кандидат после одной детекции 0.51 и одного «промаха» с тем же весом падает до 0.26
(среднее 0.51 и 0). Робот бросает цель по дороге. Простое исправление «ехать и к подозрительным» на dev ухудшило
результат (24.7% против 32.9%) и не принято.

**Выбор лучшего кандидата** (`best`): не отвергнутые проверкой, не «потерянные»; только надёжные (или все, если
исследование исчерпано); ранг = `conf × Σ_k w_k·m_k`, где m_k — совпадение кандидата с гипотезой k, нормированное
на лучшую (`match_vector`). Без слияния — по лучшему счёту детектора.

## 6. Политика: как робот принимает решения (`kznav/policy/`)

### 6.1. `ObjectNavPolicy.step()` (`objectnav.py:109`)

Одинакова для обоих тел. Каждый шаг:
1. `map.update(depth, camera, высота пола)` и `mark_free_disk` под роботом;
2. если есть энкодер ценности и запросы — SigLIP-оценка кадра и `value_map.update`;
3. `_perceive`: `detector.detect(rgb, queries)` → для каждой детекции маска (своя у детектора или от SAM, иначе
   рамка) → `memory.add` → `memory.end_frame` (слияние уверенности);
4. `_decide(pose)` → `Decision(kind, path_xy, target_xy, reason, candidate_id, n_frontiers)`.

Виды решений: `spin` (осмотр), `explore` (к фронтиру), `approach` (к кандидату), `face` (повернуться к кандидату),
`stop`, `no_plan` (сейчас некуда — осмотреться), `no_frontiers` (конец: исследовать нечего).

### 6.2. Логика `_decide` по шагам (`objectnav.py:145`)

```
1. Осмотр: первые N шагов — поворот на 360° (колёсный: 1 рад/с × 0.5 с → 13 шагов; агент: 12 поворотов по 30°).
2. cand = лучший кандидат.
   Пока cand есть и он ближе stop_distance (0.6 м до его ближайшей точки):
     а) без проверки VLM: если его видели за последние 3 шага → СТОП;
     б) если в этом кадре его не видно → «face» (повернуться), до 8 шагов; не нашёлся → «потерян», следующий;
     в) с проверкой: verifier.check(кроп) →
          stop   → СТОП;
          wait   → подъехать ближе (радиус подъезда 0.3 м вместо 0.5) за более крупным видом;
          reject → кандидат отвергнут навсегда, взять следующего.
3. Планирование: сначала с запасом (радиус + 3 см), если ничего полезного не достижимо — «впритык» (только радиус):
     если есть cand и до свободной клетки рядом с ним (≤ 0.5 м от его точек) есть путь → «approach»;
     иначе фронтиры → лучший → «explore».
4. Фронтиров нет и слияние включено: «исследование исчерпано» → подозрительные кандидаты становятся допустимыми.
5. Ничего не достижимо 5 раз подряд → «no_frontiers» (эпизод кончается).
```

`_path_to_candidate`: ищет в окне вокруг точек кандидата свободные клетки ближе радиуса подъезда, берёт
достижимую с минимальной стоимостью пути и строит путь до неё.

### 6.3. Планировщик (`planner.py: GridPlanner`)

Работает **только по карте робота** (navmesh политика не видит).
- **Запрещённые клетки**: препятствия, раздутые на радиус робота + 3 см (0.20 м) — или на чистый радиус (0.17 м)
  в режиме «впритык», для узких проходов и ножек столов.
- **Стоимость клетки**: 1 для известной свободной, **1.5 для неизвестной** (оптимистичное исследование: можно
  планировать через неизвестное, но дороже), плюс штраф близости к препятствию `1·max(0, 1 − d/0.3 м)` — пути
  держатся от стен.
- **Граф**: 8-связный; вес ребра = длина × средняя стоимость двух клеток; диагональ запрещена, если заняты обе
  ортогональные соседки (нельзя «срезать угол»).
- **Алгоритм Дейкстры** из клетки робота (`scipy.sparse.csgraph.dijkstra`) — один поиск даёт стоимость пути до
  **всех** клеток, поэтому все фронтиры и кандидаты ранжируются одним вызовом. Поиск идёт в обрезке: наблюдаемая
  область + запрошенные клетки + 1 м.
- Если робот стоит внутри раздутой зоны (прижат к стене) — старт в ближайшей свободной клетке в радиусе 0.3 м.
- `simplify_path`: жадное «спрямление» — от текущей точки берётся самая дальняя точка пути, видимая по прямой без
  запрещённых клеток.

### 6.4. Контроллер pure pursuit (`controller.py`) — только колёсный робот

Следование по ломаной пути:
- цель достигнута, если до последней точки < 0.1 м;
- **точка упреждения**: первая точка пути на расстоянии L = 0.2 м от робота (пересечение окружности с отрезками;
  индекс отрезка только растёт, робот не возвращается);
- угол до неё α; если |α| > 0.8 рад — **поворот на месте** с ω = ±1 рад/с;
- иначе кривизна **k = 2·sin α / L**, скорость v = 0.3·min(1, расстояние до конца / 0.5 м), не больше ω_max/|k|,
  не меньше 0.05; **ω = k·v**.

Lookahead 0.2 м, а не 0.3: с 0.3 робот срезал углы и задевал препятствия (D-018).

### 6.5. Исполнитель (`run/episode.py: Executor`)

Превращает решение в движение и следит за проблемами.

**Колёсный робот.** Одно решение = 0.5 с = 5 тиков по 0.1 с.
- `spin` / `no_plan` → вращение 1 рад/с; `face` → поворот к цели (ω = min(1, 2·|ошибка|));
- путь → на каждом тике `ctrl.command(pose)` → `drive`;
- **датчик обрыва** сработал → назад 0.15 м/с на 1 с, о месте сообщается политике;
- **нет прогресса** (`_check_progress`): 2 решения подряд с командой вперёд ≥ 0.1 м/с, а сдвиг < 3 см → назад 1 с.
  Место упора возвращается политике, она ставит на карту **виртуальное препятствие** радиуса 8 см прямо перед
  роботом (`on_blocked`) и строит путь в обход. После 3 упоров в одном месте (в пределах 15 см) назад больше не
  сдаёт — решает монитор застревания.

**Стандартный агент.** Одно решение = одно действие:
- точка пути, до которой ≥ 0.25 м (`lookahead`); если ошибка курса > 25° (`heading_tolerance`) — поворот на 30°,
  иначе шаг вперёд;
- если `move_forward` остановлен navmesh (сдвиг < половины шага) — сообщить политике упор (`mark_collisions`,
  D-063). Без этого агент толкался в стену, и треть шагов уходила впустую. Исправление дало +8 п. успеха с
  идеальным детектором (65.3% → 73.3%).

### 6.6. Проверка перед остановкой (`verification.py: Verifier`)

**Когда зовётся.** Только когда лучший кандидат ближе 0.6 м **и** виден в текущем кадре. Кроп = рамка + 25% контекста
с каждой стороны, не меньше 48 пикселей (`crop_bounds`). Вызов VLM (`backend.verify_candidate(crop, VerifyQuery(
target, lang))`) делается, если:
- у этого кандидата было меньше 3 вызовов;
- и это первый вызов, или кроп вырос хотя бы вдвое (робот подъехал, вид стал крупнее и информативнее).

**Что возвращает VLM.** Вероятность «да» P(yes) из logprobs первого токена ответа (подробно в 7.5). Она
пропускается через калибратор (`p_cal`) и добавляется к свидетельствам кандидата.

**Накопление свидетельств** (`belief.py: CandidateEvidence`). Несколько видов одного объекта сливаются в log-odds
вокруг базовой доли π (доля настоящих целей среди проверок в калибровочных данных):

  **logit P = logit π + γ · Σ_i (logit q_i − logit π)**, γ = 0.5

γ < 1 учитывает, что виды одного объекта коррелированы: три взгляда на один стул — не три независимых свидетельства.

**D-069 (исправлено 2026-10-15):** раньше γ применялся и к первому взгляду, поэтому один ответ должен был быть
заметно выше подобранного порога (у Qolda ≥ 0.42 вместо 0.30). С `policy.belief.first_view_full: true` первый
взгляд засчитывается полностью (P = q₁), γ — только для повторных.

**Решение** (`check`):
- P ≥ порог остановки → **stop** (порог: 0.30 для Qolda, 0.41 для Qwen после калибровки; 0.6 без калибровки);
- P < 0.25 → **reject** (кандидат отвергнут навсегда);
- 3 вызова исчерпаны или 4 шага без нового вида → reject;
- иначе **wait**: подъехать ближе за лучшим видом.

### 6.7. Байесовская вера в гипотезы (`belief.py: HypothesisBelief`)

Разбор даёт K гипотез с весами («double bed» 0.5, «bed with pillows» 0.3…). Предполагается, что одна из них —
«правильный» способ искать цель. Каждая проверка кандидата c даёт информацию о том, какая гипотеза правильная:
- m_k ∈ [0, 1] — насколько детектор связал c с гипотезой k (нормированный счёт);
- если гипотеза k правильная, c — цель с вероятностью **ρ_k = ρ_wrong + (ρ_right − ρ_wrong)·m_k**
  (ρ_right = 0.7, ρ_wrong = 0.1);
- ответ проверки входит как «виртуальное свидетельство» с отношением правдоподобия **λ = odds(q)/odds(π)**;
- правдоподобие: **P(кроп | h_k) ∝ ρ_k·λ + (1 − ρ_k)**;
- обновление: **w_k ← w_k · P(кроп | h_k)^β**, нормировка, нижняя граница веса 0.01.

Свойства (покрыты тестами): q = π не меняет веса; одинаковые m_k не меняют веса; обновления коммутируют; граница
веса не даёт одной уверенной ошибке навсегда убить гипотезу. Новые веса сразу идут в карту ценности
(`policy.query_weights`) и в ранжирование кандидатов.

### 6.8. Калибровка проверки (`calibration.py`, `tools/fit_calibration.py`) — H4

**Проблема.** Сырой P(yes) модели не равен реальной частоте. Qwen говорит 0.98 про чужие предметы
(переуверенность); Qolda на настоящей цели часто даёт 0.44 (недоуверенность). Общий порог 0.6 несправедлив к обеим.

**Platt scaling** (`PlattCalibrator`): **p_cal = sigmoid(a·logit(p) + b)**. Параметры a, b подбираются
максимизацией правдоподобия на dev-вызовах методом Ньютона с поиском шага (backtracking, Lin, Lin & Weng 2007).
Используются сглаженные цели Platt: (n₊+1)/(n₊+2) для положительных и 1/(n₋+2) для отрицательных — защита от
переобучения на крайних ответах. Без поиска шага Ньютон расходился на Qwen, которая отвечает почти только 0 и 1
(a ≈ −10¹², D-042). Есть и изотоническая калибровка (`IsotonicCalibrator`, алгоритм PAV), но выбрана Platt.

**Порог** (`choose_threshold`): перебираются наблюдённые вероятности, выбирается максимизирующая **F1** (баланс
точности и полноты). Есть вариант «минимальная точность».

**Честная оценка** (`fit_stop_rule`): вызовы делятся на 5 фолдов **по эпизодам** (вызовы одного эпизода
коррелированы), калибровка и порог каждого фолда подбираются на остальных — оценка «вне фолда».

**Метка «правильный ответ»** — по содержимому кропа: ≥ 30% пикселей рамки принадлежат цели (по семантике,
D-042).

**Артефакт** `calib/<модель>_dev.json`: калибратор, порог, базовая доля, бэкенд, **хэш промпта проверки**, список
dev-эпизодов. Раннер **отказывается** применять артефакт к эпизодам, на которых его подбирали
(`assert_disjoint_from`), и к другой модели или промпту.

**Итог (D-067).** Qolda: 1707 вызовов, ECE 0.071 → 0.033, порог 0.30. Qwen: 1142 вызова, ECE 0.137 → 0.017, порог
0.41. AUROC (насколько модель различает цель и не цель): Qolda 0.80 на всех языках; Qwen 0.93 на en и 0.84 на kk.
Калибровка исправляет **шкалу** уверенности, но не учит модель лучше различать.

## 7. Языковой модуль (`kznav/language/`)

### 7.1. Контракт VLM-бэкенда (`base.py: VLMBackend`)

Навигационный код общается с **любой** моделью через три метода:

| метод | когда | вход → выход |
|---|---|---|
| `parse_goal(text, lang)` | раз за эпизод (кэшируется) | команда → `GoalHypotheses(target, hypotheses[en, w], attributes, rooms, landmarks)` |
| `verify_candidate(image, query)` | у кандидата в зоне остановки | кроп + `VerifyQuery(target, lang)` → `VerificationResult(p_target, source, coverage, answer_text, label_from_text)` |
| `describe(image, prompt)` | прогрев и диагностика | картинка → текст |

Методы устроены как **шаблонный метод**: базовый класс вычисляет ключ входа (хэш метода, промпта и входа),
засекает время, собирает все попытки (HTTP и повторы JSON) и **всегда** отправляет `CallRecord` в «сток» (sink),
даже при ошибке. Подкласс реализует только `_parse_goal`, `_verify`, `_describe`. Так каждый вызов модели попадает
в `vlm_calls.jsonl` с сырым ответом сервера, а все картинки — в `images/<sha256>.png` (без потерь).

Ошибки: `TransportError` — сервер недоступен, таймаут, 5xx после повторов; эпизод считается сбоем инфраструктуры и
будет перезапущен, это не ошибка модели (D-046). `InvalidOutputError` — модель не выдала валидный JSON за 3
попытки; это **ошибка модели**, этап «query».

Бэкенды (`language/backends/`):
- `openai_compat.py` — любой сервер с OpenAI-совместимым API chat/completions;
- `qolda.py`, `qwen_vl.py` — наследники, проверяют конфиг: **режим «думания» обязан быть выключен явно в каждом
  запросе** (пилот: Think проигрывает по всем осям и иногда возвращает пустой ответ); у Qwen запрещены
  Thinking-чекпоинты;
- `mock.py` — детерминированная заглушка без GPU (для тестов);
- `replay.py` — повтор сохранённых вызовов из `vlm_calls.jsonl` (воспроизводимость без модели).

### 7.2. Разбор команды (`goal_parsing.py`, `prompts/default/parse_goal/v2.yaml`)

**Промпт v2** (D-043): системная инструкция на казахском («Сен үй роботының пәрмен интерпретаторысың…»), JSON-схема
ответа, правила (target — в словарной форме на языке команды; 3–5 английских визуальных гипотез с весами 0..1,
самая вероятная первой; комнаты и ориентиры) и **два примера** (қолшатыр → umbrella, шелек → bucket). Плюс правило:
«не повторяй предметы из примеров». В v1 был один пример, и обе модели, не зная слова, копировали его
(саба → umbrella).

**Цикл разбора** (`run_parse_loop`), одинаковый для всех моделей:
1. сгенерировать ответ (температура 0 — детерминизм);
2. `jsonx.extract_json_object`: убрать блоки `<think>`, взять JSON из ```json-ограды или первый сбалансированный
   `{…}`, простить висящие запятые — чтобы ошибки JSON были ошибками модели, а не парсера;
3. валидация **pydantic** (`schemas.py`): гипотезы только латиницей (кириллица → ошибка, детектор английский), вес в
   [0, 1], 1–8 гипотез;
4. `normalized()`: склеить дубликаты, нормировать веса к сумме 1, отсортировать по весу;
5. ошибка → повтор с текстом ошибки (`retry_template`), до 3 попыток.

**Режимы цели** (`goal.py: GoalSettings`, группа конфига `goal`):

| режим | что получает детектор | зачем |
|---|---|---|
| `multi` | все гипотезы VLM с весами | **метод** |
| `top1` | только самая весомая гипотеза | нужны ли несколько гипотез (D-038) |
| `mt_command` | NLLB переводит команду на английский, дальше всё по-английски (разбор, проверка) | «перевести, потом модель» (D-039, D-066) |
| `mt_word` | NLLB переводит одно слово-название, без VLM-разбора | VLFM с переводчиком |

`GoalCache` кэширует разбор по (текст, язык, категория): при температуре 0 он детерминирован. Стоимость вызова всё
равно начисляется каждому эпизоду, потому что настоящий робот разбирал бы каждую команду.

### 7.3. Лексикон и языковые метрики (`lexicon.py`, `lexicon/hm3d_objectnav.yaml`)

Для каждой категории — допустимые названия: en (chair, armchair), kk (орындық, кресло), ru (стул, кресло).
- `target_match`: разобранный target совпадает с одной из форм языка команды после нормализации (регистр,
  пунктуация); подстроки не считаются, словоформы перечисляются явно;
- `hypothesis_match`: хоть одна английская гипотеза **содержит** название категории как последовательность слов
  («large wooden chair» содержит «chair»), с лёгким снятием множественного числа.

**`hypothesis_match = False` → этап провала «query»**: модель не поняла, что искать (Qwen: «төсек» → «open door»).
Это привилегированная метка для анализа; политика её не видит.

### 7.4. Команды (`commands.py`, `commands/natural/*.yaml`)

Банк естественных команд (D-048): каждая команда написана носителем **параллельно** на kk, kk_ru и en с одним
смыслом; второй носитель её проверяет. Роли:
- **dev**-команды (12 штук) — для настройки промптов и порогов, черновики допустимы;
- **test**-команды — только одобренные, только для отчётных прогонов; без одобренной команды категории тестовый
  прогон откажется запускаться.

Какая команда достанется эпизоду, решает `stable_index(episode_id + "|command")`. Поэтому **в каждом языке и каждом
плече эпизод получает одну и ту же команду**: язык меняется, а всё остальное — нет.

### 7.5. Проверка: из ответа модели в вероятность (`prompts.py`, `logprobs.py`)

Промпт `verify_candidate/v1` — на языке команды (kk_ru → kk): «Суреттегі негізгі зат «{target}» болып табыла ма? Тек
«иә» немесе «жоқ» деп жауап бер.» Вопрос переформулирован так, чтобы частица всегда была «ма»: в пилоте «ба/па»
после разных слов давали неграмматичные вопросы.

**Вероятность.** Сервер возвращает 10 самых вероятных **первых токенов** ответа с их log-вероятностями.
`option_probabilities`:
1. токен нормализуется (пробелы, кавычки, пунктуация, регистр);
2. токен относится к варианту «да», если он **префикс** формы ответа или форма — его префикс. Это нужно потому, что
   BPE-токенизатор Qwen3 (и Qolda, у неё та же основа) режет кириллицу побуквенно: «иә» → «и», «ә»;
3. P(yes) = масса «да» / (масса «да» + масса «нет»); `coverage` — какая доля всей массы попала на варианты.

Поэтому варианты ответа обязаны начинаться **с разных букв** (иә / жоқ, да / нет, yes / no) — это проверяется при
загрузке промпта (`assert_options_distinguishable`). Число токенов ответа — 4, температура 0.

### 7.6. HTTP-клиент (`http.py: ChatClient`)

Свой минимальный клиент на httpx, а не SDK openai: тело запроса — ровно то, что пишется в лог; сырой JSON ответа
сохраняется; SDK не делает скрытых повторов, которые исказили бы задержку. Повторяются таймауты, обрывы, 429 и 5xx
(до 3 попыток, пауза 1, 2 с); остальные 4xx не повторяются. Таймаут 60 с.

### 7.7. Серверы моделей (`servers/`)

Обе модели запускаются локальными FastAPI-серверами с одинаковым API (`/v1/chat/completions`, `/v1/models`,
`/kznav/stats`). На 12 ГБ видеокарты одновременно помещается **одна** модель; `run_matrix` сам поднимает и гасит
нужный сервер.

| | Qolda (`qolda_server.py`, порт 23333) | Qwen3-VL (`qwen_vl_server.py`, порт 23334) |
|---|---|---|
| модель | issai/Qolda, 4.3B: InternViT-300M + Qwen3-4B, дообучена на казахском | Qwen/Qwen3-VL-4B-Instruct |
| веса | bf16 | bf16 (одинаковая точность — честное сравнение) |
| картинка | InternVL-тайлы 448×448, **не больше 4** + миниатюра (без лимита число тайлов скачет 1..13, задержка двугорбая, D-007) | бюджет пикселей 448²..4·448² — **столько же, сколько видит Qolda** (D-040) |
| «думание» | выключено (`enable_thinking: false` в каждом запросе) | Instruct-версия без думания |
| logprobs | `log_softmax` первого шага генерации, top-10 | то же из сырых logits |

Почему свой сервер, а не lmdeploy или vLLM: lmdeploy 0.17 не загружает конфиг Qolda, а нам нужны первые-токенные
logprobs и контроль тайлов.

### 7.8. Переводчик (`translation.py`)

NLLB-200 distilled 600M (тот же, что в пилоте), коды `kaz_Cyrl → eng_Latn`, жадное декодирование, **на процессоре**
(видеокарта занята VLM). kk_ru подаётся как казахский: кода для смешанного языка нет. Каждый перевод логируется как
вызов модели. Пилот (D-039): NLLB передал культурный предмет правильно в 1 команде из 15 (қазан → «October»,
бесік → «the girl»), Qolda — в 11 из 15.

## 8. Эпизод и прогон (`kznav/run/`, `tools/run_eval.py`, `tools/run_matrix.py`)

### 8.1. `run_episode` — главный цикл (`run/episode.py:213`)

```
seed = SHA-256(seed прогона : id эпизода)          # случайность эпизода не зависит от соседних эпизодов
env.reseed_noise(seed); obs = env.reset(старт, курс)
localizer.reset; policy.reset(seed); executor.reset
for step in range(бюджет):                          # 800 / 500
    пиксели цели в кадре (семантика) → in_view, если ≥ 100            # привилегированно
    d = policy.step(наблюдение в системе робота)
    метки кандидатов: доля пикселей цели в их рамках этого кадра
    события проверки → events.jsonl с метками «это цель?» (по содержимому и по позиции)
    detected |= есть детекция, у которой ≥ 30% рамки — цель
    запись решения в events.jsonl; on_frame (видео / диагностика)
    stop → STOP_CALLED, выход;  no_frontiers → выход
    ticks, blocked = executor.execute(d)
    blocked → policy.on_blocked (виртуальное препятствие)
    по тикам: падение (наклон > 60° или ниже старта на 0.3 м; не для стандартного агента, D-061),
              монитор застревания (застрял > 30 с → STUCK_ABORT)
    obs = env.observe()
метрики (привилегированно): геодезика от финала до точек обзора → success, SPL, SoftSPL, DTS
метка остановки: у кандидата, где остановились, ≥ 30% рамки — цель? (иначе — по позиции, ≤ 0.3 м от AABB цели)
исход (Outcome) и этап провала (Stage) → EpisodeResult (одна строка episodes.csv, ~60 колонок)
```

Монитор застревания (`eval/robot.py: StuckMonitor`): тик «застрял», если в окне 3 с всё время была команда, а
сдвиг < 5 см (и поворот < 0.1 рад, если команда была не только вперёд). Время застревания считается с учётом окна.
Столкновения считаются как события (`count_collision_events`): касание стены подряд — одно событие, если перерыв
меньше 0.5 с.

### 8.2. `BenchmarkRunner` (`run/benchmark.py:282`)

- Эпизоды группируются **по сценам**: симулятор сцены создаётся один раз.
- Для каждого эпизода: `prepare_episode` → исключение или запуск `_run_one`.
- `_run_one`: при языковом плече `LanguageRun.goal_for` (команда → разбор) и `attach` (запросы, веса, верификатор в
  политику); без языка запрос — английское название категории (базовая линия «как VLFM»).
- **Отказы (D-046)**: исключение в эпизоде (сервер упал, ошибка симулятора) не останавливает прогон. Попытка
  пишется в `failures.csv` с трассировкой, симулятор сцены пересоздаётся. 3 отказа подряд → прогон прерывается
  (сервер лежит). При продолжении упавшие эпизоды повторяются до 2 попыток. Упавший эпизод **никогда** не пишется
  в `episodes.csv` как пройденный.
- **Продолжение (resume)**: эпизоды из `episodes.csv` / `exclusions.csv` пропускаются. Поэтому любой прогон можно
  прервать и продолжить с места; потеряется только незаконченный эпизод.
- **Видео**: у доли эпизодов, выбранной `stable_index(id + "|video")`, — **одни и те же эпизоды во всех плечах**.

`LanguageRun` создаёт бэкенд (с двумя стоками: лог прогона и список вызовов эпизода), загружает команды по роли
датасета, кэш целей, порог и калибровку. Проверяет, что артефакт калибровки подобран для этой модели и этого
промпта и не пересекается с оцениваемыми эпизодами.

### 8.3. Что пишется в папку прогона

```
manifest.json      итоговый конфиг и его хэш, git-коммит и «грязное» состояние, версии пакетов, GPU,
                   описание бэкенда с хэшами промптов, роль датасета, язык, порог, калиброван ли
episodes.csv       одна строка на эпизод: метрики, исход, этап провала, воронка, стоимость VLM, языковые метки
exclusions.csv     исключённые эпизоды с причинами
failures.csv       отказы инфраструктуры (+ failures/<эпизод>_attemptN.txt с трассировкой)
goals.csv          разобранная цель каждого эпизода
events.jsonl       по событию на шаг: решение, поза, кандидат, число детекций; события проверки; упоры
vlm_calls.jsonl    каждый вызов модели: вход, сырой ответ сервера, попытки, задержка, ошибка
images/<sha>.png   каждая картинка, отправленная модели (хранится один раз по хэшу)
summary.md         сводка прогона
video_*.mp4        видео выбранных эпизодов: камера с рамками, карта, карта ценности, текст решения
```

Строки JSONL сбрасываются на диск после каждой записи: сбой теряет максимум одну строку.

### 8.4. `tools/run_eval.py` и `tools/run_matrix.py`

- `run_eval.py`: один прогон = одна конфигурация (`--lang none|kk|kk_ru|en`, `--no-verify`, переопределения Hydra).
  Отказывается от датасета с ролью debug (для него `run_debug_episodes.py`). `--resume` продолжает папку с тем же
  конфигом (сверка хэша).
- `run_matrix.py`: **матрица** (`paper/matrices/*.yaml`) — общие переопределения + список **плеч** (у каждого свои
  переопределения, язык, сервер) × seeds. Ячейка = плечо × seed = папка `runs/matrix/<матрица>/<плечо>/seed0`.
  `plan` показывает состояние ячеек; `run` запускает незаконченные, сгруппировав по серверу (сначала без VLM, потом
  все Qolda, потом все Qwen), сам поднимает и гасит сервер (одна модель на GPU), продолжает начатые ячейки; `spec`
  пишет спецификацию таблиц статьи.

## 9. Оценка (`kznav/eval/`)

### 9.1. Метрики (`metrics.py`) — как в habitat-lab

- **l** — кратчайший путь от старта до ближайшей точки обзора (по navmesh оцениваемого тела);
- **p** — фактически пройденный путь (сумма отрезков между позициями на каждом тике);
- **d_T** — кратчайший путь от финальной позиции до ближайшей точки обзора;
- **Success** = остановка вызвана **и** d_T < 0.1 м (строгое неравенство, как в habitat-lab);
- **SPL** = Success · l / max(l, p) — успех с поправкой на длину пути;
- **SoftSPL** = max(0, 1 − d_T/l) · l / max(l, p) — частичное приближение тоже засчитывается;
- **DTS** = max(0, d_T − 0.1) — сколько не доехал до зоны успеха.

Эпизод с l ≤ 0 или l = ∞ — ошибка данных: он исключается и показывается, а не усредняется молча.

### 9.2. Исход и этап провала (`failures.py`)

**Termination** — почему кончился эпизод: stop_called, step_limit, no_frontiers, stuck_abort, fell, model_error,
sim_error. **Outcome** — один исход: success, false_stop (остановился у чужого), stop_too_far (у цели, но вне зоны),
step_limit, not_found, stuck, fell, …

**Этап провала (Stage, D-045)** — первое правило в порядке конвейера, которое сработало:

```
1. успех                                       → none
2. ошибка симулятора / сервера                 → infrastructure (не результат, перезапуск)
3. разбор не удался или ни одна гипотеза не называет категорию → query       [язык]
4. остановился: у чужого → false_stop [восприятие]; у цели, но далеко → stop_too_far [навигация]
5. застрял / упал                              → stuck                        [навигация]
6. цель ни разу не была в кадре (< 100 px)     → not_seen                     [навигация]
7. в кадре была, детектор ни разу не попал     → not_detected                 [восприятие]
8. проверка отвергла настоящую цель            → verify_reject                [восприятие]
9. иначе (видел, не отвергал, но не доехал)    → not_reached                  [навигация]
```

Группы: **язык** (query), **восприятие** (not_detected, verify_reject, false_stop), **навигация** (not_seen,
not_reached, stuck, stop_too_far).

**Почему это важно для H1.** Этапы **разбивают** все провалы: каждый провальный эпизод — ровно в одном этапе. Тогда
разрыв успеха раскладывается **точно**:

  **SR(en) − SR(kk) = Σ_этапы [доля_kk(этап) − доля_en(этап)]**

(`paper.py: gap_decomposition`, с доверительным интервалом по сценам на каждую долю). H1 поддержана, если вклад
«язык + восприятие» положителен (ДИ выше 0) и больше половины разрыва, **причём и при порядке «сначала навигация»**:
проверка чувствительности, в которой застревание и «цель не в кадре» идут первыми и всё, что объясняется навигацией,
списывается на неё.

**Метка остановки по содержимому** (D-046): остановка «у цели», если ≥ 30% рамки кандидата — пиксели цели. Метка по
позиции (кандидат ≤ 0.3 м от AABB цели) — вторичная, для чувствительности.

### 9.3. Статистика (`stats.py`, `paper.py`)

Все сравнения **парные**: оба плеча прошли одни и те же эпизоды.

| что | метод | зачем |
|---|---|---|
| ДИ доли успеха | **Wilson** | лучше нормального приближения у краёв (0% и 100%) |
| ДИ среднего | бутстреп (10 000 пересэмплирований), процентильный | без допущений о распределении |
| **ДИ при ≥ 5 сценах** | **кластерный бутстреп по сценам**: пересэмплируются целые сцены | эпизоды одной квартиры зависимы (та же планировка, те же объекты); сцен мало (20 в val) |
| p-значение контраста | **перестановочный тест со сменой знака по сценам**: при нулевой гипотезе плечи взаимозаменяемы, значит можно менять знак всех разностей сцены сразу | честный учёт зависимости внутри сцены; точный (2^k вариантов) при k ≤ 16 сценах, иначе 20 000 случайных |
| поправка на множественность | **Holm** по всем главным контрастам таблицы | семья из 5–7 сравнений; Holm мощнее Бонферрони и тоже контролирует FWER |
| вторичный тест | точный **McNemar** на несогласных парах | классика для парных бинарных исходов |
| размер эффекта | **d_z** = среднее разностей / SD разностей | для парных данных |
| взаимодействие (C2) | четвёрка (a − b) − (c − d) | «преимущество Qolda больше на kk, чем на en» |

Мельчайшее достижимое p при k сценах — 2/2^k: с малым числом сцен значимость недостижима, и это честный ответ.

### 9.4. Калибровочные метрики (`eval/calibration.py`, `photo_bench.py`)

- **ECE** (ожидаемая ошибка калибровки): вероятности раскладываются по 10 корзинам; ECE = Σ (доля корзины) ·
  |частота правды − средняя вероятность|. 0 — идеально;
- **Brier** = среднее (p − y)²;
- **AUROC** — вероятность, что случайная настоящая цель получит больший P(yes), чем случайный чужой предмет;
  0.5 — случайно, 1.0 — идеально.

### 9.5. Мощность (`power.py`, `tools/power_analysis.py`, D-049)

Сколько эпизодов нужно, чтобы заметить разницу. Модель: k сцен, у каждой свой уровень успеха и свой эффект
(разброс по сценам), доля несогласных пар ψ. Методом Монте-Карло считается мощность **того же** теста, что в
статье (смена знака по сценам, α/m). Отсюда 547 основных эпизодов (100 на категорию, растений всего 47).

## 14. Вероятные вопросы на защите и ответы

**Общая архитектура**

1. *Почему модульный подход, а не end-to-end VLM-навигация?* Можно измерить вклад каждого модуля (H1), VLM
   зовётся 3–5 раз за эпизод вместо каждого шага (скорость: шаг ~0.4 с против 3–9 с на вызов VLM), детектор общий
   для всех плеч — разница между моделями идёт от языка. Это стандарт для zero-shot ObjectNav (VLFM, ApexNav,
   SG-Nav).
2. *Что такое zero-shot здесь?* Ни одна модель не обучается на нашей задаче. Настраиваются только пороги и
   параметры, и только на dev-сценах.
3. *Чем вы отличаетесь от VLFM?* VLM разбирает команду на любом языке в несколько английских гипотез с весами;
   проверка VLM перед остановкой с калибровкой; слияние уверенности по кадрам и маски SAM; низкий колёсный робот;
   SigLIP 2 вместо BLIP-2; планировщик (алгоритм Дейкстры по своей карте) и pure pursuit вместо обученной
   PointNav.
4. *Зачем два робота?* Числа литературы получены на агенте 0.88 м. Наш пылесос видит мир иначе, поэтому главная
   таблица на пылесосе, а таблица (а) на стандартном агенте — для сравнения с опубликованным.

**Симулятор**

5. *Почему кинематика, а не физика?* Сканы HM3D физически неточны, и физический робот застревал на артефактах
   скана (D-052). Кинематика по своему navmesh сохраняет размеры, камеру, скорости и ускорения робота. Физика
   используется в исследовании устойчивости.
6. *Что такое точки обзора и почему вы их пересчитали?* Позиции не дальше 1 м от объекта, откуда он виден (≥ 100
   пикселей). Датасетные посчитаны для камеры 0.88 м; с 0.15 м видно другое, поэтому `compute_view_points`
   пересчитывает их камерой робота.
7. *Как считается геодезическое расстояние?* Кратчайший путь по navmesh (Recast/Detour в habitat-sim), до
   ближайшей точки обзора; для SPL — по navmesh оцениваемого робота.
8. *Политика видит navmesh?* Нет. Только RGB-D и свою позу. Navmesh и семантику использует только раннер для
   метрик.

**Восприятие**

9. *Как строится карта?* Log-odds occupancy grid 5 см; точки из глубины классифицируются по высоте относительно
   полосы робота; лучи очищают клетки; занятость — после 2 попаданий. Препятствие — то, во что упрётся именно этот
   робот: столешница для пылесоса проходима.
10. *Что такое фронтир?* Свободная клетка рядом с неизвестной, достижимая от робота; группы меньше 6 клеток
    отбрасываются.
11. *Как работает карта ценности?* SigLIP 2 сравнивает кадр с текстом каждой гипотезы; взвешенная сумма
    записывается в видимые клетки с уверенностью cos² от угла; фронтир выбирается по «ценность − 0.002 × путь».
12. *Почему GroundingDINO, а не YOLO?* YOLO знает 80 фиксированных классов и не понимает гипотез вроде «carved
    wooden chest». Открытый детектор ищет по тексту. С низкой камеры он и по категориям лучше закрытого (TPR 0.42
    против 0.26, D-062).
13. *Почему каждая гипотеза отдельным проходом?* Совместная подпись на кадрах низкой камеры почти не отличала кадры
    с целью от кадров без неё (AUROC 0.55 против 0.61, D-058).
14. *Зачем SAM?* Рамка включает фон; без маски 3D-позиция кандидата уезжает на стену позади. SAM даёт контур
    объекта по рамке.
15. *Что такое слияние уверенности?* Взвешенное по числу точек среднее счётов детекций кандидата; кадр, где
    кандидат должен быть виден, но не обнаружен, добавляет «0». Надёжный кандидат — от 0.45; к подозрительным едут
    только после исчерпания фронтиров. Это снижает ложные остановки базовой линии.

**Политика**

16. *Как робот решает, что делать?* Осмотр 360° → если лучший кандидат ближе 0.6 м: проверка (или остановка без
    проверки) → иначе подъезд к кандидату → иначе к лучшему фронтиру → если фронтиров нет — к подозрительным → иначе
    конец.
17. *Какой планировщик?* Дейкстра по 8-связной сетке своей карты; стоимость: известное 1, неизвестное 1.5, штраф
    у стен; препятствия раздуты на радиус робота + 3 см; один поиск даёт стоимость до всех клеток.
18. *Как робот едет по пути?* Pure pursuit: точка упреждения 0.2 м, кривизна 2·sin α / L, поворот на месте при
    ошибке курса больше 0.8 рад; ускорения ограничены.
19. *Что делает робот, если упёрся?* 2 решения без прогресса → сдаёт назад 1 с и ставит на карту виртуальное
    препятствие перед собой. У стандартного агента остановленный navmesh шаг тоже отмечается (D-063: +8 п.).

**Язык и VLM**

20. *Что делает VLM?* Дважды: разбирает команду в target и 3–5 английских гипотез с весами (раз за эпизод) и
    проверяет кандидата перед остановкой («это кровать?» → P(yes)).
21. *Почему гипотезы на английском?* Детектор и SigLIP английские. VLM — мост между казахским и английским
    визуальным миром.
22. *Как получается вероятность из ответа «иә/жоқ»?* Сервер отдаёт top-10 log-вероятностей первого токена;
    токены, являющиеся префиксами «иә» или «жоқ», суммируются; P(yes) = масса «да» / масса обоих вариантов. Варианты
    обязаны начинаться с разных букв, потому что BPE режет кириллицу побуквенно.
23. *Зачем калибровка?* У моделей разная «манера» уверенности: Qwen переуверена (0.98 на чужих предметах), Qolda
    недоуверена (0.44 на настоящих целях). Platt scaling переводит P(yes) в честную вероятность, порог max-F1
    подбирается на dev по каждой модели. ECE после калибровки: Qolda 0.033, Qwen 0.017 (вне фолда).
24. *Почему калибровка одна на модель, а не на язык?* Иначе мы бы «подкрутили» именно ту разницу между языками,
    которую измеряем.
25. *Как избегаете утечки теста в калибровку?* Калибровка подбирается только на dev-эпизодах (сцены train);
    артефакт хранит список своих эпизодов, и раннер отказывается применять его к ним; тест не трогается до
    заморозки плана.
26. *Почему температура 0?* Детерминизм: один и тот же вход даёт один и тот же ответ, эпизоды воспроизводятся, разбор
    можно кэшировать.
27. *Почему No-Think?* В пилоте режим рассуждения проигрывал по точности и задержке и иногда возвращал пустой ответ;
    его выключение проверяется кодом в каждом запросе.
28. *Как обеспечено честное сравнение Qolda и Qwen?* Одинаковые промпты, точность bf16, температура 0, одинаковый
    бюджет пикселей картинки, одни и те же эпизоды и команды, общий детектор и навигация; калибровка у каждой своя,
    но по одному правилу.
29. *Почему не просто переводчик + сильная модель?* Это проверяется вариантом «NLLB → Qwen» (D-066). В пилоте NLLB
    ломал культурные слова (1/15 против 11/15 у Qolda). На обычных предметах перевод может справиться — тогда
    аргумент за родную модель переносится на культурные предметы (H2).

**Оценка и статистика**

30. *Какие метрики?* Success, SPL, SoftSPL, DTS по определениям habitat-lab; ложные остановки, застревания;
    вызовы и задержка VLM; этап провала каждого эпизода.
31. *Как доказывается H1?* Этапы провала разбивают все неудачи, поэтому разрыв SR(en) − SR(kk) точно раскладывается
    на вклады этапов; H1 — если вклад «язык + восприятие» > 0 (ДИ) и больше половины разрыва, в том числе при
    порядке «сначала навигация».
32. *Почему единица анализа — сцена?* Эпизоды одной квартиры зависимы. ДИ — кластерным бутстрепом по сценам,
    p-значения — перестановочным тестом со сменой знака по сценам; поправка Holm на семью главных контрастов.
33. *Что значит «парное сравнение»?* Оба плеча проходят одни и те же эпизоды с одной и той же командой; сравниваются
    разности по эпизодам, это устраняет разброс сложности эпизодов.
34. *Сколько эпизодов и хватает ли?* 547 основных + 297 вложенных; размер выбран анализом мощности того же теста
    (`power.py`). На dev-выборках по 100 эпизодов ДИ ±9–12 п.: это только предварительный просмотр.
35. *Что такое «не дошёл» и что вы с этим сделали?* Цель была обнаружена, но робот не остановился у неё. Диагностика
    (D-065, 35 эпизодов) показала: уверенность цели вдвое падает после одного промаха детектора, робот бросает её.
    Простое исправление ухудшило результат и не принято — это записано как отрицательный результат.

**Ограничения (честно)**

36. *Главные ограничения?* Симуляция (не реальный робот); dev-цифры не тест; порог детектора выбран по базовой
    линии без проверки; таблица (а) сравнивается с VLFM приблизительно (их val против нашей выборки, их PointNav
    против нашего планировщика); на обычных предметах разница моделей может быть малой; одна видеокарта
    ограничивает объём.
37. *Воспроизводимость?* Детерминизм по эпизоду; манифест с хэшем конфига, git-коммитом и версиями; все вызовы
    моделей и картинки сохранены; `replay`-бэкенд повторяет языковую часть без модели; прогон продолжается с места
    без смены результата.
