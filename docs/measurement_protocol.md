# Протокол измерений

Определения, по которым считаются все числа стенда. Изменение любого пункта — новое
решение в `docs/decisions.md` и новая версия `SCHEMA_VERSION` в `kznav/eval/records.py`.

## Стандартные метрики ObjectNav (`kznav/eval/metrics.py`)

Определения — как в habitat-lab 0.2.4.

- **l** — кратчайший путь по navmesh оцениваемого embodiment от старта до ближайшей
  точки обзора цели. Считается один раз при reset.
- **p** — длина пройденного пути: сумма евклидовых расстояний между последовательными
  позициями. Позиции пишутся на **каждом такте управления**: при непрерывном движении
  длина зависит от частоты записи.
- **d_T** — кратчайший путь от финальной позы до ближайшей точки обзора.
- **Успех**: вызван stop **и** d_T < success_distance (строгое неравенство; 0.1 м
  до точки обзора).
- **SPL** = успех · l / max(l, p).
- **SoftSPL** = max(0, 1 − d_T / l) · l / max(l, p).
- **DTS** = max(0, d_T − success_distance); равен inf, если цель недостижима из
  финальной позы. Такие эпизоды исключаются из среднего DTS, их число выводится
  в столбце `n_excluded`.
- Эпизод с l ≤ 0 или l = inf — ошибка датасета или embodiment. Он не усредняется
  (ValueError).
- **Точки обзора** под embodiment (`kznav/sim/episodes.py`) считаются на сетке с шагом
  ≤ success_distance·√2 (для 0.1 м — шаг ≤ 0.141 м, по умолчанию 0.1). При более редкой
  сетке допустимая поза остановки может оказаться дальше 0.1 м от всех узлов, и успех
  зависел бы от сетки, а не от робота. Код отказывается считать с таким шагом.

## Эпизоды набора данных на роботе (`kznav/run/benchmark.py`, D-041)

- Стандартный агент (таблица (а)): navmesh и точки обзора из набора, старт как в наборе — так
  считает habitat-lab. Любой исключённый эпизод помечается в сводке.
- Колёсный робот (таблица (б)): точки обзора пересчитываются под его камеру и navmesh; старт
  прижимается к его navmesh не дальше 0.2 м; l — по его navmesh до ближайшей точки обзора.
- Эпизод, который нельзя пройти этим роботом, не запускается и попадает в `exclusions.csv` с
  причиной: цели нет в семантической разметке, нет точек обзора, старт вне navmesh, цель
  недостижима, старт уже в точке обзора. В отчётах указывается число исключённых по причинам;
  SR считается по запущенным эпизодам, исключённые не засчитываются ни как успех, ни как провал.
- **Сбои** (D-046) — исключение во время эпизода: сервер модели недоступен, ошибка симулятора, баг.
  Эпизод не записывается в `episodes.csv`. Попытка пишется в `failures.csv`, трейсбек — в `failures/`.
  Прогон продолжается с пересозданным симулятором сцены. `run.max_consecutive_failures` сбоев подряд
  останавливают прогон. Продолжение прогона повторяет упавшие эпизоды до `run.max_episode_attempts`.
  - Недоступность сервера (`TransportError`) — всегда сбой инфраструктуры: она не становится ни
    «неразобранной командой», ни «отказом верификатора».
  - Невалидный ответ модели после повторов (`InvalidOutputError`) — результат метода, эпизод остаётся
    в данных.
- **Команды** (D-048): для отчётных прогонов — банк естественных команд
  (`commands/natural/<набор>.yaml`, `docs/command_authoring.md`), одобренные test-команды.
  Команда выбирается по хешу id эпизода и одинакова во всех языках и плечах. Шаблоны разработчика —
  только для отладки.

## Задержка и стоимость VLM (`kznav/language/base.py`)

- `latency_total_s` — `time.perf_counter()` от входа в метод бэкенда до возврата. Это время,
  которое робот ждёт: включает кодирование изображения, все HTTP-повторы и все повторы
  разбора JSON. Задержка каждой попытки записывается отдельно.
- Прогрев: `warmup_calls` вызовов в начале прогона помечаются `warmup=True` и
  исключаются из статистики.
- Запросы к модели идут по одному (без параллельных запросов к одному серверу).
  В манифест пишется, делят ли модель и симулятор одну видеокарту.
- Задержка на изображениях зависит от числа тайлов (D-007). Параметры изображения
  фиксируются в конфиге и пишутся в каждый вызов (`inputs.sent_image`).
- В отчётах: медиана и p95 по вызовам и суммарное время VLM на эпизод.
- Перевод (режимы `goal=mt_command` / `goal=mt_word`, D-039) — не вызов VLM. Его время —
  отдельная колонка `translation_latency_s` (тот же протокол `perf_counter`), в `vlm_calls`
  и `vlm_latency_*` не входит. Как и разбор, перевод команды приписывается каждому эпизоду
  с этой командой. Сам вызов пишется в `vlm_calls.jsonl` с `method: translate`.

## Режимы цели и языковые колонки (`kznav/language/goal.py`)

- `goal_mode`: `multi` (метод), `top1` (D-038), `mt_command`, `mt_word` (D-039).
- `n_hypotheses` и `hypothesis_match` считаются по гипотезам, которые получил конвейер
  (детектор, карта ценности, веса), а не по всем, что написала модель. Всё написанное
  моделью хранится в `goals.csv` (`parsed_hypotheses`). Для `multi` это одно и то же.
- `target_match` сравнивается с формами языка, на котором шёл разбор (`pipeline_lang`):
  после `mt_command` — с английскими. В `mt_word` разбора нет, `target_match` пуст.

## Верификация и калибровка

- P(цель) берётся из logprobs первого токена ответа: масса вероятности на
  «да»-варианты, нормированная на «да» + «нет». Для каждого вызова пишется покрытая
  масса (`coverage`). Нет logprobs — `p_target = None`, `source = unavailable`,
  и это считается отдельно.
- ECE: по умолчанию бинарный, 10 равных корзин, корзина (lo, hi]; также Brier и
  reliability diagram (D-013).
- Метка вызова проверки для калибровки и статистики — по содержимому: в рамке детекции не меньше
  30 % пикселей цели (`is_goal_by_content`, D-042). Метка по положению кандидата
  (`is_goal_privileged`, ближе 0.3 м к цели) остаётся в логе для сравнения со старыми прогонами.
- Калибратор (Platt или изотонический) и порог остановки подбираются **только на dev**.
  Артефакт калибровки хранит id dev-эпизодов, и прогон отказывается стартовать,
  если они пересекаются с оцениваемыми эпизодами.

## Столкновения и застревание (`kznav/eval/robot.py`)

- **Столкновение** — нарастающий фронт неопорного контакта робота со сценой (определение
  по embodiment — ниже). Контакты, начавшиеся раньше чем через `merge_gap_s` после конца
  предыдущего, — одно столкновение.
- **Застревание**: на такте t, на протяжении всего окна [t − W, t], движение
  командовалось на каждом такте, и
  - если в окне командовалось поступательное движение — смещение < d_min
    (поворот на месте не считается продвижением);
  - иначе (только поворот) — изменение курса < yaw_min.

  Время застревания включает окно, доказавшее застревание (D-012). Если текущее
  застревание длится дольше `abort_after_s`, эпизод завершается как STUCK.
- **Восстановление** (колёсный робот, D-020) — отдельный счётчик `recoveries`. Оно не
  прерывает подсчёт застревания.

Столкновения у двух embodiment измеряются по-разному, поэтому их числа сравнимы
только внутри одного embodiment:

- **колёсный робот** — контакт Bullet любого звена со сценой, кроме опорного контакта
  колеса или опорного колеса (нормаль в пределах ~45° от вертикали), с силой выше
  `min_normal_force_n`;
- **агент Habitat** — флаг скольжения по navmesh (`agent.act()`), как в habitat-lab.

## Классы исходов (`kznav/eval/failures.py`)

Каждый эпизод получает ровно один класс: SUCCESS, FALSE_STOP (остановка не у цели),
STOP_TOO_FAR (у цели, но вне зоны успеха), STOP_UNLABELED, STUCK, COLLISIONS,
STEP_LIMIT, NOT_FOUND, MODEL_FAILURE, SIM_FAILURE.

Отдельно пишется «воронка» по истинной разметке:

1. цель попадала в кадр;
2. цель была задетектирована;
3. цель получила положительную верификацию.

Так видно, где рвётся цепочка «язык → визуальная привязка». Определения
(`configs/eval/default.yaml: funnel`):

- **в кадре** — в каком-либо кадре видно ≥ 100 пикселей любого экземпляра цели;
- **задетектирована** — у какой-либо детекции ≥ 30% пикселей рамки принадлежат цели;
- **остановка у цели** (D-046) — по содержимому: в последней рамке детекции кандидата, у которого
  робот остановился, не меньше 30% пикселей цели (`stop_box_goal_fraction`, тот же порог, что для
  верификации). Рамка берётся из кадра, где кандидат был замечен последний раз. Если семантического
  кадра нет, используется метка по положению: кандидат ближе 0.3 м к рамке какого-либо экземпляра
  цели. Обе метки пишутся, `stop_label_source` говорит, какая использована. Это отличает
  STOP_TOO_FAR от FALSE_STOP.
  - Положение кандидата — медиана точек маски. У сегментатора-рамки в маску попадает фон, поэтому
    метка по положению смещена в сторону FALSE_STOP.
- **отказ верификатора цели** — верификатор отклонил кандидата, рамка которого по содержимому —
  цель (`goal_ever_verify_rejected`).

## Этап провала (`kznav/eval/failures.py: attribute_failure`, D-045)

Каждому неуспешному эпизоду приписывается ровно один этап — первое сработавшее правило
(порядок конвейера):

1. инфраструктура (ошибка симулятора, ошибка модели после успешного разбора);
2. `query` — разбор не удался или ни один запрос не называет категорию цели (лексикон);
3. остановка: `false_stop` / `stop_too_far` / `stop_unlabeled` по метке кандидата;
4. `stuck` — застревание, падение, лимит столкновений;
5. `not_seen` — цель ни разу не была в кадре;
6. `not_detected` — была в кадре, детектор с запросами эпизода её не нашёл;
7. `verify_reject` — верификатор отклонил цель;
8. `not_reached` — остальное: цель найдена, но робот до неё не добрался (бюджет, план, потеря).

Группы: язык — `query`; привязка — `not_detected`, `verify_reject`, `false_stop`; навигация —
`not_seen`, `not_reached`, `stuck`, `stop_too_far`.

Этапы разбивают провалы без пересечений, поэтому разность SR двух плеч точно раскладывается
по этапам (`paper.gap_decomposition`).

Анализ чувствительности — порядок «навигация первой»: после инфраструктуры сначала `stuck`, затем
`not_seen` для любого эпизода, где цель не была в кадре (остановка или нет), потом остальные правила.

## Статистика (`kznav/eval/stats.py`, `paper.py`, D-047)

Полный план анализа — `docs/analysis_plan.md`.

- Сиды сначала усредняются по эпизоду.
- Единица вывода — **сцена**: эпизоды одной сцены зависимы (одна планировка, одни объекты).
  - ДИ — перцентильный бутстрэп по сценам (10 000 повторов, фиксированный seed), если сцен ≥ 5;
    иначе — Уилсон для 0/1 и бутстрэп по эпизодам.
  - p — перестановочный тест со сменой знака парных разностей целых сцен (точный при ≤ 16 сценах,
    иначе 20 000 перестановок). При одной сцене p = 1: значимость там недостижима.
- Сравнение моделей — парное, на одних и тех же эпизодах и командах. Считаются:
  - разность с ДИ;
  - Cohen's d_z по эпизодам;
  - p по сценам с поправкой Holm на семейство основных контрастов;
  - точный тест Мак-Немара по парам эпизод–сид — вторичный.
- Взаимодействие (a − b) − (c − d) считается тем же способом (например, преимущество родной модели
  в казахском минус в английском).
- Анализы чувствительности:
  - кластеры по командам;
  - метка остановки по положению;
  - без эпизодов с ошибочным вызовом модели;
  - порядок этапов «навигация первой».
- Непарные контрасты (культурные против универсальных слов) — Cohen's d с общим SD
  (и поправка Хеджеса).
- Если у сравниваемых плеч разный набор эпизодов, код отказывается считать контраст. Исключение —
  эпизоды из `failures.csv`: они убираются из всех плеч контраста и считаются (`dropped_failed`).
- Объём выборки — до тестовых прогонов, `tools/power_analysis.py` (D-049).

## Разделение dev / test

- Пороги, калибровка, промпты и параметры политики настраиваются на dev: несколько
  train-сцен HM3D, не пересекающихся с val.
- val используется только для итоговых чисел.
- Собственная комната (`dataset.role: debug`) не входит ни в одну основную таблицу.
